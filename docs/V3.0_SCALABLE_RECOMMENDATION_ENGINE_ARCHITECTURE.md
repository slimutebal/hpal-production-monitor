## 05–09. Kompleksitas Eksak

Untuk satu Contractor dengan:

- `F` = jumlah DT fisik;
- `n` = jumlah source;
- setiap source dapat menerima `0..F`;
- total alokasi `≤ F`.

Jumlah allocation adalah:

```text
allocations(F, n) = C(F + n, n)
```

Ini adalah formulasi **stars-and-bars**, dan sama persis dengan yang dihitung oleh `countContractorAllocations()` sebelum `enumerateAllocations()` mematerialisasikan tuple sebenarnya.

Untuk seluruh Contractor:

```text
globalCandidates = Π(i=1..k) C(Fi + ni, ni)
```

Ini persis yang dihitung `findBlendRecommendations()` pada line 310–321 sebelum generation dimulai.

Desain closed-form reject ini sebenarnya sudah baik karena engine dapat mengetahui ukuran search space tanpa memulai partial enumeration. Masalahnya adalah ukuran ruang pencarian yang masih diizinkan melewati gate.

### Biaya `buildCandidate()`

`buildCandidate()` memiliki biaya sekitar:

```text
O(sources) per candidate
```

Pekerjaan yang dilakukan meliputi:

- Map lookup;
- relocation planning melalui `planContractorRelocations()`;
- donor/receiver scan `O(sources)`;
- allocation array untuk `flatSources`;
- allocation array untuk `relocations`;
- pembuatan string `allocationSignature`.

Untuk 10 source, biaya satu kandidat hanya beberapa puluh object write dan satu string concatenation.

Masalah muncul karena biaya kecil tersebut dikalikan jutaan hingga miliaran kandidat.

Setiap kandidat juga merupakan object JavaScript yang dipertahankan di memory, bukan primitive.

### Biaya Ranking / Sorting

Saat ini:

```text
pickBestCandidate()
  → candidates.slice()
  → .sort(comparator)
  → [0]
```

Kompleksitasnya:

```text
O(N log N)
```

Setiap comparator menjalankan chain lexicographic berisi 11 rule.

Pada rule A–E, comparator memanggil:

```text
calculateContractorStandbyMetrics()
```

yang sendiri `O(sources)`.

Namun hasil tersebut sudah di-memoize per candidate menggunakan `WeakMap`, sehingga hanya dihitung sekali per candidate object, bukan sekali setiap comparison.

Memoization ini sudah sangat penting. Komentar di source mencatat pernah terjadi regression sekitar `1s → 5s` sebelum cache ditambahkan.

Secara kasar:

```text
Ranking ≈ O(N log N × ruleCount)
```

dengan biaya metric per candidate diamortisasi menjadi `O(N)` melalui cache.

### Memory

Engine saat ini mempertahankan:

1. array `candidates` berisi seluruh candidate object;
2. array `withinTolerance` yang berisi reference ke subset candidate;
3. hasil `.slice()` di `pickBestCandidate()` yang membuat copy array baru sebelum sorting.

Peak resident memory secara efektif mendekati:

```text
3 × candidate-count dalam array slot
+
1 × candidate-count dalam fully materialized candidate objects
```

Dua dari tiga array hanya berisi reference, tetapi candidate object sendiri memiliki:

- Ni;
- ratios;
- sources array;
- relocation array;
- metadata lain.

Memory dengan demikian tetap tumbuh linear terhadap `globalCandidates`.

Pada skenario realistis 8–10 dome, jumlah ini mencapai miliaran.

### Operasi Dominan pada Skala Besar

Pada ukuran kandidat sekitar `10^5–10^6` atau lebih, candidate construction biasanya menjadi dominan karena:

- object allocation;
- per-candidate `O(sources)` work;
- garbage collection pressure.

Pada ukuran yang semakin besar, sorting kembali menjadi signifikan karena faktor `log N` dan comparator chain.

Namun bottleneck praktis terjadi lebih awal akibat candidate materialization + GC.

### Safety Bound Saat Ini

Dari `fleet-allocation.js:87-88`:

```text
MAX_ALLOCATIONS_PER_CONTRACTOR = 20,000
MAX_GLOBAL_CANDIDATES         = 200,000
```

## 16–18. V2.5 Minimum-6 Pruning

### 16. Kondisi Saat Ini

Dari source:

```text
enumerateAllocations()
```

menghasilkan semua integer:

```text
0..remaining
```

untuk setiap source.

Artinya allocation `1`, `2`, `3`, `4`, dan `5` DT tetap dihasilkan.

Aturan:

```text
0 atau ≥ 6 DT
```

baru diterapkan pada ranking melalui:

```text
isOperationalLoadingPointAllocation()
```

dan digunakan sebagai comparator rule `0`:

```text
invalidLoadingPointCount
```

Jadi kandidat dengan alokasi `1–5 DT` tetap:

1. di-generate;
2. di-build;
3. disimpan;
4. di-ranking.

Contoh regression test V2.5.1 sendiri membuktikannya:

> Kandidat valid `29/6` harus menang atas kandidat lama `30/5` yang invalid, walaupun `30/5` secara chemistry lebih dekat ke Target.

Artinya kandidat `30/5` tetap ada; hanya kalah ranking.

### Edge Case yang Ditemukan

Karena aturan `0-or-≥6` hanya berupa ranking preference, terdapat edge case:

Jika kandidat dengan allocation invalid `1–5 DT` merupakan **satu-satunya candidate yang within tolerance**, candidate tersebut tetap dapat dikembalikan sebagai recommendation `OK`.

Saat ini:

```text
withinTolerance = candidates.filter(c => c.withinTolerance)
```

tidak memeriksa `invalidLoadingPointCount`.

Belum ada test existing yang menutup kasus spesifik ini.

Jika aturan `0-or-≥6` dipindahkan menjadi generation-time feasibility, candidate tersebut tidak akan pernah ada.

Hasil scenario itu akan berubah dari:

```text
OK
```

menjadi:

```text
TARGET_NOT_ACHIEVABLE
```

Jadi ini bukan murni performance refactor. Ada perubahan perilaku domain yang sempit tetapi nyata.

Keputusan tersebut harus disampaikan eksplisit kepada Owner.

### 17. Dampak Minimum-6 Pruning

Perhitungan exact tuple count jika setiap source hanya boleh:

```text
{0} ∪ [6, F]
```

### 18. Apakah Minimum-6 Saja Cukup?

Tidak.

Minimum-6 pruning menghapus sekitar:

```text
76% – 99.7%
```

dari raw search space.

Ini merupakan optimisasi murah yang sangat kuat dan sebaiknya memang dipindahkan ke generation-time feasibility.

Namun persentase reduction bukan metrik yang cukup pada skala combinatorial.

Contoh:

```text

```

Masih melewati limit `200k`.

```text

```

setelah pruning.

> Minimum-6 pruning mengurangi koefisien ledakan kombinatorial, tetapi tidak mengubah bentuk kompleksitasnya.

Search space tetap:

```text
Π C'(Fi, ni)
```

dan tetap meledak pada skala operasional normal.

Minimum-6 adalah **necessary first-line filter**, tetapi bukan jawaban penuh V3.0.

## 20. Chemical Feasibility Pruning — Ni Bounds

Ini merupakan teknik dengan leverage tertinggi yang ditemukan dalam audit.

Karena final blend Ni adalah weighted average terhadap tonnage, maka untuk partial allocation dapat dihitung range konservatif final Ni tanpa membuka seluruh kombinasi di group yang belum diproses.

Untuk setiap open Contractor group:

```text
compute:
  minAchievableWeightedNi
  maxAchievableWeightedNi
```

berdasarkan feasible extreme allocations:

- lowest-Ni-source-heavy;
- highest-Ni-source-heavy;

dengan tetap menghormati:

- fleet conservation;
- feasibility `0-or-≥6`.

Lalu:

```text
finalNiBound =
(
  fixedWeightedNiSum
  + Σ openGroupBounds
)
/
(
  fixedTonnage
  + Σ openGroupTonnageBounds
)
```

Jika range:

```text
[minFinalNi, maxFinalNi]
```

tidak memiliki intersection dengan:

```text
[targetNi - tolerance, targetNi + tolerance]
```

maka seluruh branch dapat dipangkas sebelum satu pun leaf candidate dibangun.

Ini dapat dibuat **exact**.

Syarat bound hanyalah:

> konservatif — jangan pernah mengecualikan nilai yang secara nyata masih dapat dicapai.

Bound tidak harus tight.

Teknik ini juga sesuai dengan struktur existing engine karena Contractor memang sudah didekomposisi sebelum Cartesian combine.

## 21. Contractor-Level Decomposition / Pareto Pruning

Audit mengevaluasi apakah candidate allocation pada setiap Contractor dapat dikompresi menjadi frontier kecil sebelum cross-Contractor combination.

Beberapa ranking dimension memang dapat didekomposisi persis per Contractor karena relocation antar Contractor dilarang.

Invariant tersebut sudah dikunci oleh test:

```text
No cross-Contractor movement
```

### Exactly Decomposable

Berikut metric yang sepenuhnya ditentukan oleh allocation satu Contractor:

- `totalMovedUnits` — rule G;
- contribution ke `activeSourceCount` — rule I;
- continuity metrics A/C/D;
- `invalidLoadingPointCount` — rule 0.

### Aggregated, Bukan Fully Decomposable

- `totalActiveUnits` — rule B  
  Dapat dijumlahkan, sehingga mudah di-bound.

- `estimatedNi / absoluteDeviation` — rule H  
  Membutuhkan chemistry bound.

- `Hopper Pattern simplicityKey` — rule F  
  Bergantung pada global higher/LGLO split.

Untuk rule F, frontier per Contractor harus membawa pasangan:

```text
(higherUnits, lgloUnits)
```

bukan hanya satu scalar.

### Valid Pareto Dominance

State A hanya boleh dianggap mendominasi state B jika semua dimension yang relevan memenuhi arah dominance secara bersamaan.

Tidak boleh menggunakan weighted scalar tersembunyi.

Ranking existing adalah ordered lexicographic chain, sehingga frontier compression harus menjaga struktur yang sama.

Ini implementable, tetapi rawan error jika arah dominance satu metric saja salah.

## 22. Dynamic Programming

Secara teoritis DP membutuhkan state seperti:

```text
(
  Contractor index,
  cumulative active units,
  cumulative weighted-Ni numerator,
  cumulative tonnage,
  loading-point pattern so far
)
```

Masalahnya:

- Ni bersifat continuous;
- tonnage juga continuous;
- input decimal diproses melalui `parseDecimalInput()`;
- requirement existing meminta boundary test dilakukan pada full precision.

Untuk membuat state DP finite, Ni/tonnage harus didiskretisasi ke bucket.

Ini dapat menyebabkan:

- candidate yang sebenarnya within tolerance dianggap out;
- candidate yang sebenarnya out dianggap within.

Hal tersebut bertentangan dengan requirement:

> jangan pernah membulatkan kontribusi pile sebelum summation.

### Assessment

DP tidak viable sebagai exact technique tanpa discretization yang menurunkan akurasi.

**Tidak direkomendasikan untuk default V3.0 exact path.**

## 23. Branch-and-Bound

Ini adalah teknik utama yang menggabungkan temuan audit.

Traversal dilakukan satu Contractor group pada satu waktu.

Setiap node merepresentasikan partial assignment.

Bound yang tersedia:

- chemistry bound dari §20;
- decomposable continuity/relocation metrics dari §21;
- accumulator untuk Hopper Pattern simplicity;
- active-unit bound;
- Ni-deviation bound.

Node dipangkas ketika dapat dibuktikan bahwa:

> tidak ada completion dari node tersebut yang dapat mengalahkan current incumbent menurut comparator lexicographic existing.

Ini menjaga exactness karena search tidak mengubah ranking. Search hanya menolak branch yang secara matematis tidak mungkin menang.

### Correctness

Exact, jika semua bound konservatif.

### Worst-Case Complexity

Secara teoritis sama dengan exhaustive search pada adversarial input:

```text
O(full search space)
```

Namun realistic input dapat dipangkas jauh lebih awal.

### Hard Case

Scenario E extreme:

```text
10 dome
1 Contractor
100 DT
```

memiliki Tier 1 sangat besar.

Setelah incumbent bagus ditemukan, chemistry dan continuity bound dapat memangkas banyak branch, tetapi tidak ada jaminan semua input akan selesai cepat.

Karena itu tetap diperlukan explicit budget.

### Implementation Risk

Moderate.

Kesalahan paling berbahaya adalah bound yang terlalu sempit sehingga true winner ikut ter-prune.

### Determinism

Dapat dipertahankan jika traversal mengikuti canonical order:

1. normalized Contractor;
2. normalized Pile ID.

Tidak diperlukan randomization.

## 24. Best-First / Priority Search

Node dapat dieksplorasi menggunakan urutan priority yang sama dengan final ranking:

1. invalid loading point minimum;
2. utilization maksimum;
3. continuity metric terbaik;
4. dst.

Keuntungan:

- strong incumbent ditemukan lebih cepat;
- branch-and-bound menjadi lebih efektif.

Tetapi best-first saja **bukan exact termination proof**.

Tanpa conservative bound:

> engine hanya menemukan candidate yang tampak paling baik lebih cepat, tetapi tidak dapat membuktikan candidate tersebut global optimum.

### Recommendation

Gunakan best-first sebagai traversal strategy **di dalam exact branch-and-bound**, bukan sebagai standalone approximate search.

## 25. Heuristic / Beam Search

**Klasifikasi: APPROXIMATE**

Beam search mempertahankan hanya top-K partial states pada setiap depth.

Kelebihan:

- workload bounded;
- scalable;
- memory predictable.

Namun beam search tidak dapat menjamin winner sama dengan exhaustive search.

State yang terlihat buruk setelah 2 dari 7 Contractor dapat menjadi global winner setelah 5 Contractor berikutnya ditambahkan.

Jika state tersebut terbuang oleh beam width, true winner hilang.

### Kesimpulan

Beam search tidak boleh ditampilkan sebagai equivalent terhadap exact engine.

Jika suatu hari digunakan sebagai fallback, hasil harus memiliki UI status berbeda, misalnya:

```text
APPROXIMATE_RESULT
```

bukan `OK` atau `TARGET_NOT_ACHIEVABLE` seolah-olah optimality sudah dibuktikan.

Audit ini **tidak merekomendasikan beam search untuk initial V3.0**.

## 26. MILP-Style Formulation

Secara struktur domain ini mirip integer programming:

- integer active DT per source;
- implicit binary active/closed per loading point;
- linear Ni constraint;
- same-Contractor fleet conservation;
- lexicographic multi-objective ranking.

Namun general-purpose MILP solver membutuhkan:

- generic constraint layer;
- dependency tambahan;
- LP relaxation;
- solver integration;
- complexity yang tidak diperlukan aplikasi lain.

### Assessment

Custom domain-specific Branch-and-Bound sudah mengambil bagian yang paling berguna dari MILP:

- bounding;
- pruning;
- integer feasibility.

Untuk browser app tanpa dependency solver, bespoke B&B adalah pilihan yang lebih proporsional.

## 27. Web Worker

Web Worker adalah masalah terpisah dari kompleksitas algoritma.

Manfaat Worker:

- UI thread tidak freeze;
- scrolling tetap responsif;
- typing/rendering tetap responsif;
- cooperative cancellation dapat memakai `postMessage`;
- progress dapat dilaporkan.

Namun Worker tidak mengurangi jumlah computation.

```text
12 trillion candidate di Worker
=
tetap 12 trillion candidate
```

Bedanya tab tidak freeze saat search gagal.

Ada serialization cost melalui structured clone, tetapi input/output engine relatif kecil:

- puluhan source;
- satu result object.

### Decision

**Recommended, tetapi bukan load-bearing scalability fix.**

Worker sebaiknya ditambahkan setelah search sudah memiliki:

- pruning;
- branch-and-bound;
- explicit node/time budget.

Pada worst concentrated case, Worker menjadi lebih penting karena bounded search pun mungkin memerlukan visible wall-clock time.

## 28–29. Streaming Candidates & O(N) Winner Selection

### 28. Current Materialization Problem

Saat ini engine membuat:

```text
(a) candidates[]
(b) withinTolerance[]
(c) candidates.slice() sebelum sort
```

Streaming design cukup mempertahankan dua incumbent:

```text
bestWithinTolerance = null
bestAttainable      = null
```

Untuk setiap candidate `c`:

```text
if bestAttainable is null
   or compareBestAttainable(c, bestAttainable) < 0:
    bestAttainable = c

if c.withinTolerance
   and (
        bestWithinTolerance is null
        or compareWithinTolerance(c, bestWithinTolerance) < 0
   ):
    bestWithinTolerance = c
```

Final result:

```text
bestWithinTolerance ?? bestAttainable
```

Ini menjaga semantic existing:

- `OK` jika ada within-tolerance candidate;
- `TARGET_NOT_ACHIEVABLE` jika tidak.

Memory menjadi:

```text
O(1) incumbents
+
O(search depth) recursion stack
```

bukan `O(candidateCount)`.

### Exactness

Streaming minimum selection adalah exact dan order-independent selama comparator transitive.

Comparator existing menggunakan lexicographic ordered rules, sehingga property ini terpenuhi.

### 29. `pickBestCandidate()` Usage

Audit menemukan `pickBestCandidate()` dipanggil hanya di dua lokasi:

- `blending-recommendation.js:354`
- `blending-recommendation.js:378`

Dan di kedua lokasi hanya element `[0]` dari sorted result yang digunakan.

Tidak ada caller lain yang membutuhkan full sorted list.

Jadi:

```text
O(N log N) sorting
```

dapat diganti dengan:

```text
O(N) single-pass minimum selection
```

tanpa mengubah output.

Dalam arsitektur streaming, optimisasi ini menjadi bagian natural dari search baru.

## 30–33. Semantics yang Wajib Bertahan

## 30. Exactness Requirement

Ni harus dipertahankan pada full precision.

Boundary test existing:

```text
abs(estimatedNi - targetNi) <= tolerance + 1e-9
```

`1e-9` hanya untuk mengompensasi floating summation noise.

Bukan untuk memperlebar business tolerance.

Teknik yang melakukan discretization/rounding internal tidak dapat dianggap exact.

---

## 31. Determinism Requirement

Canonical ordering saat ini:

1. Contractor normalized ascending;
2. Pile ID normalized ascending;
3. final `allocationSignature` tie-break.

Test existing juga mengunci source-order independence.

Arsitektur B&B/best-first harus mempertahankan canonical visitation order yang sama agar:

- tie-break tetap konsisten;
- hasil reproducible;
- input array order tidak memengaruhi winner.

### WITHIN_TOLERANCE — 11 Rules

| Rule | Kriteria | Decomposability |

| C | minimalkan worst per-Contractor standby ratio | per-Contractor exact |
| D | paling sedikit Contractor yang membutuhkan >5% mitigation | per-Contractor exact |
| E | paling sedikit current loading point yang tidak digunakan sama sekali | per-Contractor exact |

| G | minimalkan total relocated units | per-Contractor exact |
| H | minimalkan absolute Ni deviation | global continuous / chemistry bound |
| I | minimalkan active source count | per-Contractor exact / sum |

### BEST_ATTAINABLE — 6 Rules

| Rule | Kriteria |
|---|---|
| 1 | minimalkan absolute Ni deviation |
| 2 | maksimalkan total active units |
| 3 | Hopper Pattern paling sederhana |
| 4 | minimalkan relocated units |
| 5 | minimalkan active source count |
| 6 | deterministic tie-break |

Tidak ada performance reason untuk mengubah urutan rule tersebut.

Ranking order atau weighting tidak boleh diubah dalam performance redesign karena itu akan menjadi perubahan domain logic tersembunyi.

## 33. Continuity Boundary Recommendation

Aturan:

```text
0 atau ≥ 6 DT
```

merupakan physical feasibility constraint untuk satu loading point.

Constraint ini dapat dievaluasi langsung ketika allocation satu source dipilih dan tidak membutuhkan future lookahead.

Karena itu aturan ini secara arsitektural lebih tepat berada pada:

```text
generation-time feasibility
```

Sementara logic:

- `SPLIT`
- `REPLACE`
- `CLOSE_DOME`
- `REDUCE`

bergantung pada bentuk final selected candidate.

Logic tersebut harus tetap berada setelah candidate selection.

### Recommended Boundary

```text
0-or-≥6
    → generation-time feasibility

SPLIT / REPLACE / CLOSE_DOME / REDUCE
    → post-selected-candidate
```

Namun semantic edge case pada §16 harus menjadi explicit Owner decision.

# 35–40. Recommended V3.0 Architecture

## 35. Rekomendasi

**Option J — Layered Exact Hybrid**

Urutan layer dalam satu search pass:

1. **Generation-time operational feasibility**  
   Setiap source hanya boleh:

   ```text
   {0} ∪ [6, remainingFleet]
   ```

2. **Contractor-level decomposition**  
   Existing grouping tetap dipertahankan, tetapi setiap Contractor state membawa decomposable metrics.

3. **Branch-and-bound traversal, ordered best-first**  
   Contractor dikombinasikan satu demi satu dalam canonical order.

4. **Chemistry-bound pruning**  
   Branch yang final Ni range-nya tidak dapat mencapai tolerance dipotong.

5. **Dominance pruning**  
   Partial state yang secara lexicographic tidak mungkin mengalahkan incumbent dipangkas.

6. **Streaming incumbent tracking**

   ```text
   bestWithinTolerance
   bestAttainable
   ```

   Tidak ada full `candidates[]`.

7. **Explicit safety budget**  
   Node/time budget menggantikan size-based gate sebagai runtime safety mechanism.

8. **Optional Web Worker**  
   Digunakan jika benchmark worst concentrated case menunjukkan visible UI blocking.

## 36. Mengapa Arsitektur Ini Dipilih

Option J merupakan satu-satunya opsi pada audit yang sekaligus:

- exact;
- tidak membutuhkan discretization;
- tidak menggunakan beam width;
- langsung menyerang combinatorial blowup;
- dapat dibangun incremental;
- mempertahankan ranking rule existing;
- cocok untuk mobile dengan memory flat;
- tetap deterministic.

Satu-satunya domain-adjacent issue yang perlu explicit approval adalah perpindahan rule `0-or-≥6` dari ranking preference menjadi generation feasibility.

## 37. Exact vs Approximate Classification

### Recommended Architecture

```text
EXACT
```

Arsitektur yang direkomendasikan dapat mengembalikan winner identik terhadap exhaustive search untuk:

- `WITHIN_TOLERANCE`;
- `TARGET_NOT_ACHIEVABLE`.

Dengan syarat:

- semua bound konservatif;
- ranking order tidak diubah;
- tie-break rule tetap sama.

Tidak ada:

- heuristic;
- rounding;
- discretization;
- beam width.

Beam search tetap hanya future optional fallback yang harus diberi label approximate.

## 38. Expected Complexity Improvement

Tidak ada satu Big-O sederhana yang dapat menggambarkan B&B karena actual cost bergantung pada bentuk input.

Namun layer improvement-nya jelas:

### Generation Feasibility

Menghapus sekitar:

```text
76% – 99.7%
```

raw allocations dari awal.

### Chemistry Bound

Menghapus seluruh subtree ketika achievable Ni interval tidak dapat menyentuh tolerance.

### Best-First Ordering

Mendapat incumbent kuat lebih awal sehingga dominance pruning menjadi semakin agresif.

### Streaming

Menghilangkan:

```text
O(candidateCount)
```

memory retention.

### Remaining Hard Case

```text
1 Contractor
8–10+ dome
large fleet
```

masih merupakan bentuk problem yang benar-benar combinatorial.

Kasus itu tidak boleh "diklaim selesai" hanya dengan optimisme terhadap pruning.

Explicit budget tetap dibutuhkan.

## 39. Mobile Suitability

Arsitektur baru jauh lebih cocok untuk mobile karena:

- incumbent memory tetap flat;
- tidak ada jutaan candidate object ditahan;
- node/time budget membatasi worst-case work;
- Worker dapat menjaga main thread responsive;
- serialization payload kecil.

Ini merupakan peningkatan besar dibanding current engine yang harus fully materialize semua candidate yang lolos closed-form gate.

## 40. Remaining Pathological Cases

Kasus paling sulit adalah satu Contractor dengan banyak dome aktif bersamaan, kira-kira:

```text
n ≳ 8–10 dome
```

Contoh:

```text
F = 100
n = 10
```

Tier 1 saja sudah puluhan miliar state.

Dua opsi jujur untuk kondisi ini:

### Option A — Bounded Exact Search

Gunakan node/time budget.

Jika budget habis sebelum optimality terbukti, return status eksplisit seperti:

```text
SEARCH_LIMIT_REACHED
```

dengan pesan:

```text
best result found so far — optimality not proven
```

Hasil tersebut tidak boleh diam-diam diberi status `OK`.

### Option B — Future Approximate Fallback

Beam/heuristic search hanya untuk bentuk pathological tertentu, dengan UI disclosure eksplisit.

Audit tidak merekomendasikan memperluas scope initial V3.0 untuk menyelesaikan seluruh extreme case dengan mengorbankan exactness.

# 47–50. Test Strategy

## 47. Golden Result Compatibility

Untuk semua input yang masih dapat diselesaikan current exhaustive engine, assert byte-for-byte equality pada:

- result `status`;
- selected `activeUnits` per source;
- `estimatedNi` full precision;
- `fleetUtilization`;
- `relocations`;
- ranking winner identity melalui `allocationSignature`;
- candidate input ke Hopper Pattern.

Ini adalah guardrail paling penting dan harus tersedia sebelum Phase 2.

---

## 48. Randomized Differential Testing

Generate ribuan small scenarios yang masih tractable untuk exhaustive engine.

Variasi minimal:

- Contractor count `1–4`;
- multi-dome dalam Contractor yang sama;
- varied tonnes/DT;
- LGLO / MGLO / HGLO mix;
- minimum-6 boundary;
- scenario `5-vs-6 DT`;
- target di dalam achievable range;
- target di luar achievable range;
- deliberate ties;
- relocation-heavy same-Contractor fleet.

Jalankan:

```text
old engine
vs
new engine
```

dan assert output identik sesuai field §47.

Setiap mismatch adalah:

```text
Phase-blocking bug
```

bukan rounding difference yang boleh diabaikan.

# 52–57. Risks

## 52. Mathematical Correctness Risks

Risiko tertinggi adalah chemistry/dominance bound yang terlalu ketat.

Jika bound salah:

> true winner dapat ter-prune secara diam-diam.

Mitigasi utama:

- golden differential test;
- randomized differential test;
- exhaustive reference engine sampai Phase 4.

### Rule F Risk

Hopper Pattern simplicity adalah ranking dimension yang paling global dan paling sulit didekomposisi.

Envelope logic di sini membutuhkan test tambahan.

### Minimum-6 Semantic Risk

Perubahan dari ranking preference ke feasibility rule dapat mengubah edge-case result.

Harus explicit Owner decision.

## 53. Performance Risks

### Single-Contractor / Many-Dome

Jika real operation rutin memiliki Contractor dengan `8+` dome aktif simultan, budget/Worker/future heuristic harus dianggap bagian nyata scope, bukan footnote.

### Best-First Assumption

Best-first sangat efektif bila true winner dekat top priority order.

Audit menunjukkan ini masuk akal untuk common case, tetapi adversarial input tetap dapat memaksa deep exploration.

Karena itu budget tetap wajib.

# Kesimpulan

Masalah utama current V2.x recommendation engine bukan berada pada continuity, actions, Hopper Pattern, atau recovery.

Masalahnya berada pada:

```text
candidate generation
+
Cartesian combination
+
full materialization
```

yang menghasilkan pertumbuhan kombinatorial:

```text
globalCandidates = Π C(Fi + ni, ni)
```

Raising limits tidak menyelesaikan masalah.

Minimum-6 pruning sangat berguna tetapi tidak cukup.

Tiered utilization search memperbaiki traversal order tetapi tidak membatasi search space.

Arsitektur V3.0 yang paling kuat berdasarkan audit ini adalah:

```text
Generation-time feasibility
        ↓
Contractor decomposition
        ↓
Exact Branch-and-Bound
        ↓
Best-first traversal
        ↓
Chemistry + dominance pruning
        ↓
Streaming incumbents
        ↓
Explicit node/time budget
        ↓
Optional Web Worker
```

Target utamanya adalah:

- tetap exact;
- menjaga full-precision Ni;
- mempertahankan deterministic ranking;
- menghasilkan winner yang sama dengan exhaustive engine;
- menghilangkan full candidate materialization;
- scalable hingga operational envelope `10 dome / 7 Contractor / 100+ DT`;
- tetap jujur terhadap pathological concentrated cases yang belum dapat dijamin cepat secara matematis.

Perubahan `0-or-≥6` menjadi generation-time feasibility adalah satu-satunya perubahan yang memiliki semantic edge case dan harus disetujui Owner secara eksplisit sebelum implementation phase berikutnya.
