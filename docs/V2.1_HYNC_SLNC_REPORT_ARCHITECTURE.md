## Section 1 — Executive Summary

V2.1 was created to let the Report page (`#/report`) produce the same *DAILY PRODUCTION GEOLOGY REPORT* output for a second buyer, **SLNC**, without duplicating the Report workflow. Monitor already recognized SLNC data (`detectBuyer()` in `index.html`) before this change; Report did not — it was hardcoded to HYNC end-to-end (fixed labels, a single `hync-profile.js` with no buyer parameter, no reading of the workbook's `备注` column at all).

What changed from V2.0:

- **HYNC remains fully supported.** Every HYNC-specific calculation, label, and contractor lookup that existed before V2.1 is still reachable through unchanged, byte-identical logic (see [Section 17](#section-17--safety-and-regression-boundaries)).
- **SLNC was added** as a second buyer, sharing the same parsing engine, calculation rules, ore-class thresholds, loading-area options, and contractor table as HYNC.
- **One shared Report UI** (`#/report`) serves both buyers — there is no `#/report-hync` or `#/report-slnc` route.
- **Buyer mismatch protection** was added: the buyer is auto-detected from two independent sources (previous-report text and the workbook), and Step 2 stays blocked unless both sources agree.
- **ESG is not part of V2.1.** No ESG code, ESG detection, or ESG UI exists anywhere in the current working tree.

V2.1 moves the Report module from a single hardcoded HYNC implementation toward a **buyer-profile architecture** — a shared parsing/calculation engine plus small, buyer-specific identity modules. This generalization is scoped to the Report module only. Monitor, Settings, routing, the contractor data source, and the app shell are unchanged by V2.1; the application as a whole is not "fully generic," only Report's buyer handling is.

## Section 4 — Application Routing

`js/router.js` defines exactly three routes via `ROUTE_PATTERN = /^#\/(monitor|report|settings)$/`: `#/monitor`, `#/report`, `#/settings`. Anything else (empty hash, unknown segment, trailing characters) falls back to `monitor`, the `DEFAULT_ROUTE`. This pattern is unchanged by V2.1.

- HYNC and SLNC both use the single `#/report` route — `router.js` has no buyer-specific route, and `report-page.js` never inspects the route for buyer information.
- Buyer-specific routes were intentionally not created, per the task's requirement for one shared Report UI.
- `js/app.js`'s `init()` calls `initReportPage()` once at bootstrap, which builds `#page-report`'s DOM a single time (`buildShellMarkup()` runs once). Route changes only toggle a page's `.is-active` class (`router.js`'s `applyRoute()`); they never rebuild `#page-report`.
- Because `reportState` (`report-state.js`) is a module-scoped singleton object created once at import time, and the DOM is never rebuilt, Report state (including the new buyer fields) survives navigating Report → Monitor → Report within the same session.

## Section 6 — Shared Profile Architecture

**`profile-registry.js`** — buyer identification only:
- `BUYER_HYNC`/`BUYER_SLNC`/`SUPPORTED_BUYERS` token constants.
- `REMARK_PREFIX_TO_BUYER` map (`{ SCHY: 'HYNC', SCSL: 'SLNC' }`), private to this module.
- `buyerFromRemark(rawValue)` — classifies one `备注` cell.
- `buyerFromPrevText(text)` — classifies previous-report text.
- `getProfile(buyer)` — returns `{ buyer, label: buyer }` for a supported buyer, `null` otherwise.

**`shared-report-profile.js`** — everything that is genuinely identical for both buyers:
- Workbook parsing (`parseWeighbridgeWorkbook`): sheet selection (`SHEET_NAME = '过磅明细'`), header mapping (`REQUIRED_HEADERS`), valid-row determination, date/time parsing, dome/grade extraction, contractor resolution.
- Shift and date handling (unchanged 05:01–17:00 day-shift window, night-shift continuation rule).
- Ore-class calculation (`classifyOreClass` — thresholds unchanged).
- Totals calculation (`calculateTotals` — Daily/WTD/MTD/YTD, unchanged formulas).
- Report-text generation (`buildReportText`), parameterized by a `buyer` string for the two buyer-specific output lines.
- `AREA_OPTIONS` (`BR1`/`BR23E`/`BR23W`/`DS`) and `LOADING_POINT_ORDER` (`DS`/`BR1`/`BR23E`/`BR23W`) — shared, buyer-agnostic constants.

**`hync-profile.js`** — identity + compatibility only:
- `HYNC_BUYER = 'HYNC'`, `HYNC_REMARK_PREFIX = 'SCHY'`, `HYNC_PROFILE` object.
- Backward-compatible exports (`HYNC_SHEET_NAME`, `HYNC_REQUIRED_HEADERS`, `HYNC_AREA_OPTIONS`, `parseHyncPrevText`, `parseHyncWorkbook`, `buildHyncFileSummary`, `calculateHyncTotals`, `buildHyncReportText`) — each a thin wrapper delegating to `shared-report-profile.js` (with `buyer: 'HYNC'` bound where relevant). No HYNC-only *behavioral* configuration remains in this file beyond the buyer identity itself — HYNC's actual contractor priority/alias/spec parsing all live in the shared module now (see Section 17 for why this is safe).

**`slnc-profile.js`** — identity + convenience wrappers only:
- `SLNC_BUYER = 'SLNC'`, `SLNC_REMARK_PREFIX = 'SCSL'`, `SLNC_PROFILE` object.
- `parseSlncPrevText`, `parseSlncWorkbook`, `buildSlncFileSummary`, `calculateSlncTotals`, `buildSlncReportText` — symmetrical wrappers around the same shared functions with `buyer: 'SLNC'` bound. No SLNC-only configuration exists; SLNC uses the same contractor table (via a normalization fallback, Section 14), the same ore-class thresholds, and the same area options as HYNC.

**Why calculations are shared rather than copied:** the header set, sheet name, spec-column format (once `NI:` is treated as optional), ore-class thresholds, and Daily/WTD/MTD/YTD formulas were confirmed identical for both buyers before this architecture was built (real SLNC sample workbooks were inspected; Monitor's own `classifyOre()`/`NI_BASE_MAP` in `index.html` already treats HYNC and SLNC identically). Copying `hync-profile.js` into a near-duplicate `slnc-profile.js` would have meant maintaining the same Daily/WTD/MTD/YTD logic, contractor bucketing, and ore-class thresholds in two places with no behavioral reason to diverge.

**Import direction (confirmed acyclic):**

```text
report-page.js
  ├─→ report-state.js
  ├─→ report-utils.js
  ├─→ profiles/shared-report-profile.js
  │      ├─→ report-utils.js
  │      ├─→ services/contractor-adapter.js
  │      └─→ profiles/profile-registry.js   (leaf: no internal imports)
  └─→ profiles/profile-registry.js

profiles/hync-profile.js  ─→ profiles/shared-report-profile.js, report-utils.js, services/contractor-adapter.js
profiles/slnc-profile.js  ─→ profiles/shared-report-profile.js, report-utils.js, services/contractor-adapter.js
```

`profile-registry.js` is a dependency-free leaf (its own header comment states this explicitly, so `shared-report-profile.js` can import it without risking a cycle back through `hync-profile.js`/`slnc-profile.js`). Neither `hync-profile.js` nor `slnc-profile.js` is imported by `shared-report-profile.js`, `profile-registry.js`, or each other. `report-page.js` does not import either profile-identity file at all — it goes straight to `shared-report-profile.js` + `profile-registry.js` with an explicit buyer string. The graph has no cycle.

## Section 7 — Buyer Identification

### From previous-report text

`profile-registry.js`'s `buyerFromPrevText(text)`:

```js
const hasHync = /FPP\s+HYNC/i.test(raw);
const hasSlnc = /FPP\s+SLNC/i.test(raw);
if (hasHync && hasSlnc) return { status: 'ambiguous' };
if (hasHync) return { status: 'ok', buyer: BUYER_HYNC };
if (hasSlnc) return { status: 'ok', buyer: BUYER_SLNC };
return { status: 'notFound' };
```

- Case-insensitive (`/i` flag).
- Whitespace-tolerant (`\s+` matches any run of spaces/newlines between `FPP` and the buyer token).
- Both `FPP HYNC` and `FPP SLNC` present → `ambiguous` (blocked, see Section 8).
- Neither present → `notFound` (blocked; `report-page.js` never assigns a buyer in this case — no silent HYNC fallback exists anywhere in `recomputeBuyerResolution`).

### From the workbook's `备注` column

`shared-report-profile.js`'s `parseWeighbridgeWorkbook()` locates the column by header name (`header.indexOf(REMARK_HEADER)`, where `REMARK_HEADER = '备注'`), not by a fixed column index — if the sheet's column order changes, the lookup still finds it by name. Each valid data row's raw cell value is classified by `profile-registry.js`'s `buyerFromRemark()`:

```js
const value = String(rawValue == null ? '' : rawValue).trim().toUpperCase();
if (!value) return { status: 'blank' };
const prefix = Object.keys(REMARK_PREFIX_TO_BUYER).find((p) => value.startsWith(p));
return prefix ? { status: 'ok', buyer: REMARK_PREFIX_TO_BUYER[prefix] } : { status: 'unknown' };
```

- Trimmed and upper-cased before comparison.
- `SCSL` prefix → SLNC. `SCHY` prefix → HYNC.
- Only `startsWith()` on the prefix is checked — the complete FPP number (the digits after the prefix) is never compared.
- "Valid row" here means the same rows `parseWeighbridgeWorkbook`'s main loop already treats as data (a row is skipped entirely, remark included, if its `车号` cell is blank) — header, blank, and non-data rows are never classified.

### Why multiple codes for one buyer are valid

```text
SCSL-0000033
SCSL-0000034
SCSL-0000035
```

All three share the `SCSL` prefix, so `buyerFromRemark()` classifies all three rows as `{ status: 'ok', buyer: 'SLNC' }`. `resolveWorkbookBuyer()` (in `shared-report-profile.js`) tallies rows into a `Set` of *buyers*, not a set of *codes* — three different codes collapse into one entry (`'SLNC'`) in that set, so `buyersFound.size === 1` and the workbook resolves cleanly to SLNC with no issue. The same reasoning applies to:

```text
SCHY-0000010
SCHY-0000011
```

— both classify as HYNC, both collapse into one `Set` entry, no issue is raised. **Multiple codes for one buyer are normal and intentionally produce no popup or warning** — only a prefix mismatch (a different buyer's prefix, a blank cell, or an unrecognized value) produces an issue. This was verified against real SLNC sample workbooks during implementation, including one file containing two different `SCSL-xxxxxxx` codes in contiguous blocks and another containing two different codes interleaved throughout the sheet — both resolved to a clean `SLNC` with `workbookBuyerIssues: null`.

## Section 8 — Buyer Consistency Validation

Implemented in `report-page.js`'s `recomputeBuyerResolution()`, using `reportState.previousReportBuyer`, `reportState.workbookBuyer`, and `reportState.workbookBuyerIssues`:

| Previous Report | Workbook | Result (`BUYER_STATUS`) |
| --- | --- | --- |
| HYNC | HYNC | `confirmed` |
| SLNC | SLNC | `confirmed` |
| HYNC | SLNC | `mismatch` — blocked |
| SLNC | HYNC | `mismatch` — blocked |
| Missing (not yet detected) | Recognized | `pendingWorkbook` — blocked until text is valid |
| Recognized | Missing (not yet uploaded) | `pendingPreviousReport` — blocked until workbook is valid |
| Ambiguous (`FPP HYNC` and `FPP SLNC` both present) | Any | `ambiguousPreviousReport` — blocked |
| Any | Mixed HYNC/SLNC rows in one workbook | `invalidWorkbook` — blocked |
| Any | Unknown/blank `备注` on a valid row | `invalidWorkbook` — blocked |

Notes confirmed from the code:

- Step 2 remains blocked until `buyerStatus === BUYER_STATUS.CONFIRMED`: `goToStep2()` calls `recomputeBuyerResolution()` and pushes a blocking error (`buyerGateErrorMessage()`) into the same `errors` array as the other Step 1 field checks whenever the status isn't `CONFIRMED`. `goToStep3()` independently re-checks `reportState.buyerValidationStatus !== BUYER_STATUS.CONFIRMED` before generating anything.
- A mismatch does not clear the user's inputs: neither `recomputeBuyerResolution()` nor `openBuyerMismatchPopup()` touches `els.prevText.value` or `reportState.parsed`/`fileName`.
- Correcting either input recalculates buyer resolution automatically: the `prevText` `input` listener and `handleFileChange()` both call `recomputeBuyerResolution({ openPopupOnNewMismatch: true })` on every change.
- A stale `resolvedBuyer` cannot remain active after a mismatch: `reportState.resolvedBuyer = status === BUYER_STATUS.CONFIRMED ? resolvedBuyer : (isProblem ? null : resolvedBuyer)` — for every problem status (`mismatch`, `invalidWorkbook`, `ambiguousPreviousReport`), `resolvedBuyer` is explicitly forced to `null`.
- Generated output always uses the currently confirmed buyer: `goToStep3()` reads `reportState.resolvedBuyer` (not a cached/earlier value) when calling `buildReportText`, and if a confirmed buyer changes to a different one (or is lost), `recomputeBuyerResolution()` clears `reportState.reportText = ''` so a stale report cannot survive under the wrong buyer's label.

Exact FPP-code equality between the previous-report text and the workbook is **not** implemented and not required — the previous-report text never contains a full FPP code (only the `FPP HYNC`/`FPP SLNC` buyer token), so only buyer-level comparison is possible or performed.

## Section 9 — Report State Model

All fields below are read directly from `report-state.js`'s `createDefaultState()` and `BUYER_STATUS`.

| Field | Purpose | Initial value | Update trigger | Reset behavior | Stored / derived |
| --- | --- | --- | --- | --- | --- |
| `previousReportBuyer` | Buyer detected from the previous-report textarea | `null` | Recomputed on every `prevText` input event and at the Step 1→2 gate | Cleared to `null` by `resetReportState()` | Derived (recomputed from `els.prevText.value` each call, not incrementally patched) |
| `workbookBuyer` | Buyer detected from the uploaded workbook's `备注` column | `null` | Set by `handleFileChange()` after a successful parse; cleared on parse failure or reset | Cleared to `null` | Stored (comes from `parseWeighbridgeWorkbook()`'s return value; not re-derived elsewhere) |
| `workbookBuyerIssues` | `null`, or an array of `{ type: 'mixed' \| 'unrecognized', ... }` records when the workbook's `备注` column doesn't cleanly resolve | `null` | Same trigger as `workbookBuyer` | Cleared to `null` | Stored (from `parseWeighbridgeWorkbook()`) |
| `resolvedBuyer` | The buyer the rest of the UI/output should use — confirmed, or provisional if only one source has reported in | `null` | Recomputed every time `recomputeBuyerResolution()` runs | Cleared to `null` | Derived from the other four fields |
| `buyerValidationStatus` | One of the seven `BUYER_STATUS` values | `BUYER_STATUS.UNKNOWN` (`'unknown'`) | Recomputed every time `recomputeBuyerResolution()` runs | Reset to `'unknown'` | Derived |

**`BUYER_STATUS` values actually defined in code:** `UNKNOWN: 'unknown'`, `PENDING_WORKBOOK: 'pendingWorkbook'`, `PENDING_PREVIOUS_REPORT: 'pendingPreviousReport'`, `CONFIRMED: 'confirmed'`, `MISMATCH: 'mismatch'`, `INVALID_WORKBOOK: 'invalidWorkbook'`, `AMBIGUOUS_PREVIOUS_REPORT: 'ambiguousPreviousReport'`.

- **Module scope / route navigation:** `reportState` is exported once from `report-state.js` and mutated in place everywhere (`Object.assign` in `resetReportState()`, direct property writes elsewhere) — it is not recreated on navigation, so Report → Monitor → Report preserves every field above, consistent with the rest of `reportState` (unchanged behavior from V2.0, documented in `docs/V2.0_ARCHITECTURE_AND_ROADMAP.md` section 12).
- **Browser refresh:** not preserved. `report-state.js`'s own header comment states the module "is NOT persisted to localStorage/IndexedDB, so it is lost on refresh, tab close, or an explicit reset" — this is unchanged by V2.1; no new persistence was added for the buyer fields.
- **Reset:** `resetReportState()` calls `Object.assign(reportState, createDefaultState())`, which includes all five buyer fields — a reset clears buyer state exactly like every other field, with no special-casing.
- **Invalidating stale output:** as described in Section 8, `recomputeBuyerResolution()` clears `reportState.reportText` when a previously confirmed buyer changes to a different value (or is lost).

## Section 10 — Report Workflow

**Step 1 — Input** (`goToStep2()` in `report-page.js`):
- Paste previous report (`els.prevText`) — validated on every keystroke for buyer detection (`recomputeBuyerResolution`), and parsed for Date/Daily/WTD/MTD/YTD (`parsePrevText`) only at the Step 1→2 gate.
- Upload workbook (`handleFileChange`) — parsed immediately on file selection (`parseWeighbridgeWorkbook`), which also runs buyer detection for that source and stores `workbookBuyer`/`workbookBuyerIssues`.
- Buyer detection from both sources happens continuously (on text input, on file change); buyer *match validation* (the gate) happens when the user clicks "Lanjut →" (`goToStep2()`), which re-runs `recomputeBuyerResolution()` one more time and blocks with `errors.push(buyerGateErrorMessage(...))` if the status isn't `CONFIRMED`.
- Previous totals (Daily/WTD/MTD/YTD from the pasted text) are parsed at the same gate (`parsePrevText`), with any parse errors added to the same blocking `errors` list.
- Supporting fields (Week, PIC SCM, PIC AWK, Manpower AWK, Total Manpower) are required and validated at the same gate.

**Step 2 — Area Muat** (`renderDomeList()` / `handleDomeAreaChange()` / `goToStep3()`):
- One area required per dome (`missing = domes.filter((d) => !reportState.domeAreas[d.dome])`, blocks with a red-highlighted row list if any dome is unassigned).
- Options (`AREA_OPTIONS` in `shared-report-profile.js`, unchanged by V2.1): `BR1`, `BR23E`, `BR23W`, `DS`.
- `goToStep3()` also re-checks buyer confirmation before anything else (defense-in-depth beyond the Step 1 gate, in case the user reached Step 2 and then somehow invalidated the buyer state without re-triggering the gate).

**Step 3 — Hasil** (`goToStep3()` continued):
- Calculates totals (`calculateTotals`).
- Inserts the confirmed buyer name (`buildReportText({ buyer: reportState.resolvedBuyer, ... })`).
- Renders a preview (`renderScaleDisplay`, `renderWarnings`, the output textarea).
- Copy to clipboard (`copyOutput()` — unchanged from V2.0, uses `navigator.clipboard.writeText` with an `execCommand('copy')` fallback).

**Which validation occurs when:**
- **On every input change** (typing in the previous-report textarea, selecting a workbook file): buyer detection is recalculated and the UI labels/status line update immediately (`recomputeBuyerResolution` → `updateBuyerUI`); the mismatch popup opens only on the *transition* into a problem state (see Section 15), not on every keystroke.
- **On "Lanjut →" (Step 1→2)**: the full Step 1 validation gate runs — required-field checks, previous-report text parsing, and the buyer-confirmation gate, all surfaced together in one alert block.
- **On "Generate Laporan →" (Step 2→3)**: buyer confirmation is re-checked, then the loading-area-per-dome check runs.

## Section 11 — Dynamic UI Labels

Three states, driven by `report-page.js`'s `updateBuyerUI()`:

- **Neutral** — no buyer detected yet from either source (`reportState.resolvedBuyer`, `previousReportBuyer`, and `workbookBuyer` are all `null`). Uses the `NEUTRAL_LABELS` constant.
- **Provisional** — exactly one source has identified a buyer (`BUYER_STATUS.PENDING_WORKBOOK` or `PENDING_PREVIOUS_REPORT`). ## Section 12 — Workbook Parsing

From `shared-report-profile.js`'s `parseWeighbridgeWorkbook()`:

- **Sheet:** uses the sheet named `过磅明细` (`SHEET_NAME`) if present, otherwise falls back to the workbook's first sheet — unchanged from the pre-V2.1 HYNC-only parser.
- **Required headers** (`REQUIRED_HEADERS`, throws if any is missing): `流水号`, `车号`, `净重`, `毛重时间`, `日期`, `规格`.
- **`备注` buyer column:** located by header name (`REMARK_HEADER = '备注'`); its absence does *not* throw — every row simply reads an empty remark, which the buyer-resolution step reports as `unrecognized` (blocking progression through the buyer-validation UI rather than the file-upload error box).
- **Valid-row determination:** a row is skipped entirely if its `车号` (truck number) cell is blank; every other row is treated as a data row, including for `备注` classification.
- **Date parsing:** `parseFlexibleDate`/`parseFlexibleDateTime` accept Excel serial dates, `YYYY-MM-DD[ T]HH:MM:SS` strings, and generic parseable date strings — unchanged.
- **Shift detection:** unchanged — sorts the first 20 time-stamped rows by `毛重时间`, averages the time-of-day, and classifies `05:01–17:00` as Day Shift, otherwise Night Shift; if no row has a valid timestamp, falls back to Day Shift with a `shiftFallback` flag surfaced as a warning.
- **Net-weight conversion:** `netKg` is summed and divided by 1000 for `onShiftTon` — unchanged.
- **Dome/grade extraction (`parseSpec`):** the regex is `/^(.*?)\s*\(\s*(?:NI\s*:\s*)?([\d.,]+)\s*\)\s*$/i` — the `NI:` token is optional. The code **does** support both:
  - `DOME ( NI:1.25 )` (existing HYNC format), and
  - `DOME (1.25)` (bare-number format, per the SLNC sample workbooks inspected during implementation).
  Both produce `{ dome: 'DOME', grade: 1.25 }`. This was a deliberate extension of the original HYNC-only regex (which required a literal `NI:`), verified not to change output for any previously-valid HYNC spec string.
- **Unmatched/malformed rows:** a `规格` value that doesn't match the pattern at all does not throw — `parseSpec` falls back to `{ dome: rawSpecText || '(tanpa spesifikasi)', grade: null, valid: false }`, and `classifyOreClass(null)` returns `'-'`. A truck number not found in the contractor table (see Section 14) is recorded as `'TIDAK DIKENALI'` and added to `unmatchedTrucks`, surfaced as a non-blocking warning in Step 3 (`renderWarnings`).

## Section 13 — Calculation Rules

All formulas below are read from `shared-report-profile.js` and are unchanged from the pre-V2.1 `hync-profile.js` implementation (confirmed by direct diff during implementation — only function names changed, plus the intentional `parseSpec`/contractor-lookup extensions described in Sections 12 and 14).

- **On Shift tonnage:** sum of all valid rows' net weight (kg) ÷ 1000.
- **On Shift ritase:** count of valid rows.
- **Daily:** if Night Shift *and* the previous report's date matches the current file's date, `prev.daily + onShift`; otherwise resets to just `onShift` (Day Shift always resets; a Night Shift whose previous-report date doesn't match is also treated as stale and reset).
- **WTD / MTD / YTD:** always `prev.{wtd,mtd,ytd} + onShift` — cumulative, never reset within the parser (reset timing for these is an operational/previous-report-text concern, not something the parser decides).
- **Ore-class thresholds** (`classifyOreClass`): `grade > 1.4` → `HGLO`; `grade < 1.2` → `LGLO`; otherwise → `MGLO`.

These formulas are shared by HYNC and SLNC and were **not changed** by V2.1 — the same `calculateTotals()` and `classifyOreClass()` functions run regardless of which buyer is confirmed.

## Section 15 — Mismatch Popup

- **Purpose:** informs the user when the buyer detected from the previous-report text and the buyer detected from the workbook disagree, or when the workbook's `备注` column itself doesn't cleanly resolve to one buyer.

## Section 17 — Safety and Regression Boundaries

**Invariants confirmed unchanged by this diff:**
- Monitor behavior — `index.html`'s Monitor script was not modified by the Report changes (git diff for this feature touches no lines in `index.html`).
- HYNC calculations — `calculateTotals()` is a pure rename of the original `calculateHyncTotals()` body; zero logic changes (confirmed by direct diff during implementation).
- Daily/WTD/MTD/YTD rules — see Section 13, unchanged formulas.
- Ore-class thresholds — unchanged (`> 1.4` / `< 1.2` / else) in `classifyOreClass()`.
- Loading-area options — `AREA_OPTIONS` in `shared-report-profile.js` is still exactly `['BR1', 'BR23E', 'BR23W', 'DS']`.
- Contractor assignments — `contractor-adapter.js`'s data is untouched.
- Route structure — `router.js`'s `ROUTE_PATTERN` is unchanged.
- Copy-report format — `buildReportText()`'s line structure, order, and punctuation are unchanged from `buildHyncReportText()` except the two lines that now interpolate `${buyer}` instead of a hardcoded `HYNC` literal.
- PWA navigation fallback / cross-origin contractor synchronization — unchanged, see Section 16.

**Main regression risks introduced by the shared-code extraction:**
1. `parseSpec`'s optional-`NI:` regex is a strict superset of the original pattern — a currently-passing HYNC spec string cannot newly fail to match, but a new failure mode (a spec that now matches the *bare-number* branch when it previously fell through to the "malformed" branch) is only a risk if a legacy HYNC file ever used bare-parenthesized numbers without `NI:` for a non-grade purpose; no such data has been observed.
2. `resolveContractor`'s SLNC-normalization fallback only fires after the raw `lookupHyncContractor(carNo)` lookup fails — for existing HYNC truck ID formats (already hyphenated, no trailing `" DT"`), the fallback's regexes do not match, so it is a no-op for HYNC data. The risk surface is limited to: an HYNC-style ID that coincidentally matches `/^SCM\s+LIM\s+/i` or ends in `/\s+DT$/i` would be renormalized unnecessarily — not observed in `HYNC_DT_LIST`.
3. `parseWeighbridgeWorkbook()` now always reads and classifies `备注` even for HYNC files. If an HYNC file's `备注` column is blank or absent, `workbookBuyer` resolves to `null` with an `unrecognized` issue — this is new, intentional behavior (buyer safety) but means an HYNC workbook that previously had no `备注` column at all will now block at the buyer-confirmation gate until the previous-report text alone cannot compensate (both sources are still required to agree). This is a deliberate scope change (the whole point of V2.1), not an accidental regression, but it is a new hard requirement on the workbook that did not exist pre-V2.1.

**Compatibility exports and HYNC migration risk:** `hync-profile.js` keeps every pre-V2.1 export name (`parseHyncWorkbook`, `buildHyncReportText`, `calculateHyncTotals`, `parseHyncPrevText`, `buildHyncFileSummary`, `HYNC_SHEET_NAME`, `HYNC_REQUIRED_HEADERS`, `HYNC_AREA_OPTIONS`) with the same signatures, each delegating to the shared engine with `buyer: 'HYNC'` bound. This is confirmed in the current file — `report-page.js` does not use these compatibility exports (it calls the shared engine directly), but their presence means any other code, script, or future contributor still expecting `hync-profile.js`'s original surface will get behaviorally identical results, reducing the risk that this refactor silently breaks something outside the file this document could inspect.

## Section 20 — ESG Readiness

This section describes readiness only — no ESG behavior is designed or implemented here.

- The profile registry (`profile-registry.js`) is structurally able to hold another buyer's remark-prefix mapping and detection rule, and `shared-report-profile.js`'s engine takes a `buyer` string as a parameter already, not a hardcoded value — the mechanical seam for a third profile exists.
- The shared parser (`shared-report-profile.js`) may be reusable for ESG **only if** ESG's workbook structure is confirmed to match (same sheet name, same required headers, same `规格` format family) — this has not been checked, because no ESG workbook sample was inspected as part of V2.1.
- ESG must **not** be added by merely mapping another `备注` prefix into `profile-registry.js`. Monitor's own `index.html` code (`detectBuyer`, `parseESGRows`) already shows ESG uses a structurally different workbook (no `过磅明细` sheet, column-index-based parsing, a different `NO.NOTA`-based row filter, weight already in tons rather than kg) — evidence that ESG is not a simple third prefix on top of the current HYNC/SLNC shared engine.
- The ESG source workbook and previous-report text format must be inspected first, from real samples, before any ESG-specific code is written.
- ESG may have different headers, tables, calculations, or output format than HYNC/SLNC — none of this is assumed or pre-built by V2.1.
- ESG needs its own approved reference evidence (a real workbook, an approved previous-report text example, and an approved output format) before implementation, the same standard SLNC was held to for V2.1.
- Mixed-buyer detection (Section 8's validation matrix) must later account for ESG safely — e.g. a workbook containing ESG rows mixed with HYNC/SLNC rows is not currently a case `resolveWorkbookBuyer()` needs to consider, but would need to once a third buyer exists.
- The Report UI should remain shared only if ESG's workflow (Input → Area Muat → Hasil, the same three-step shape) is proven compatible — if ESG's process differs structurally, forcing it into the same three-step shell may not be appropriate.

**Evidence required before ESG implementation:**
1. Real ESG workbook samples.
2. ESG's `备注` (or equivalent) buyer-identification rule, or confirmation that ESG needs a different identification signal entirely.
3. An approved ESG previous-report text example.
4. An approved ESG output-format reference.
5. ESG contractor behavior (does it reuse the same `HYNC_DT_LIST`, or need its own).
6. ESG's `规格`/grade format (confirmed or ruled out to match HYNC/SLNC's).
7. Any calculation differences from the HYNC/SLNC Daily/WTD/MTD/YTD rules.
8. ESG loading-area requirements (same `BR1`/`BR23E`/`BR23W`/`DS` set, or different).
9. ESG-specific validation rules (equivalent to Section 8's matrix).
10. ESG acceptance tests, mirroring the structure of Section 22's checklist.

**V2.1 is the architectural checkpoint before ESG, not proof that ESG can be added without further analysis.**
