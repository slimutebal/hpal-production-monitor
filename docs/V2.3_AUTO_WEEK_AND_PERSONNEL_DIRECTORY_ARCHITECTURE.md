## Section 1 — Executive Summary

V2.3 is the final planned stage before HPAL Production Monitor becomes a licensed, bilingual, theme-aware, personnel-directory-driven application. It bundles six operational/data features and three application-shell features into one coherent release:

**Operational / data track:**
1. Automatic Week — derive the Report's read-only "Week" field from the active workbook's date using ISO week-number behavior (Monday–Sunday), with no manual override in V2.3.
2. Local Personnel Directory — a Settings-managed, locally stored roster of four distinct record types (SPV SCM, FRM SCM, Independent Sampler, PIC 3rd), replacing free-text Report fields.
3. Google Sheet Personnel Sync (Read) — pull the authoritative personnel roster from a dedicated `report_personnel` Google Sheet tab, mirroring the existing contractor-sync pattern.
4. Google Sheet Personnel Sync (Write) — let Settings push new/edited personnel back to the same tab, online first.
5. Optional Offline Write Queue — added only after online writes are stable, to queue personnel writes locally when offline and flush them automatically when connectivity returns.
6. Report Output Migration — wire Report's Man Power/PIC fields to the Personnel Directory instead of raw text inputs. **This intentionally changes the personnel section of the generated report's text** (Section 19.5); it is not a byte-identical migration.

**Application-shell track:**
7. Language and Localization — Indonesian/English UI switching via a centralized i18n layer.
8. Appearance — Dark/Light/Auto theme selection, **unifying the theme behavior the application already has today** (Section 13) rather than introducing theme support from zero.
9. Offline Full Access License — **(Phase 8 licensing update, 2026-08-08)** a single permanent, Owner-held local access key, verified offline via PBKDF2-HMAC-SHA-256 (Web Crypto), that gates Report, the Personnel Directory, and future licensed features behind a `FULL_ACCESS` tier, while an unlicensed `MONITOR_ONLY` tier keeps Monitor (and License/Language/Appearance in Settings) fully usable. Replaces the asymmetric signed-token / License Generator design originally planned here — see Sections 6–11.

These are not independent add-ons bolted onto separate parts of the app — they interact. The Personnel Directory and Report Output Migration are licensed operational features; Language and Appearance are not; Automatic Week only makes sense once Report already knows the workbook date (which it does today, unrelated to licensing). Section 3 defines the exact scope boundaries, and Sections 6–14 define the application-level state model, all four tracks share.

**Sequencing principle carried through this whole document:** the operational features (Automatic Week, Personnel Directory, sync, Report migration) and the two non-licensed shell features (Language, Appearance) are built and stabilized **before** the License feature is added on top (Section 22, Phase 8). Licensing is a gate placed around already-working features, not a feature built in parallel with them — this lets the license route/feature guards be tested against a complete, stable feature set instead of a moving target. During Phases 2–7, this necessarily means the licensed operational surfaces (Report, Personnel Directory) are reachable through an explicit, temporary development-time bypass rather than a real license check — Section 6.4 defines the boundaries of that bypass so it is never mistaken for a shippable state.

## Section 2 — Document Claims and Non-Claims

Stated explicitly, per the Owner's requirement that this document not overclaim:

- **Licensing is planned, not implemented.** No token format, verification code, or storage exists in the repository today.
- **Language switching is planned, not implemented.** The application is Indonesian-only today, with no i18n layer.
- **Settings-level Appearance control is planned; the underlying theme behavior is not unknown.** The application already has confirmed Dark/Light/Auto theme behavior today (Section 13.2); what is planned for V2.3 is exposing and unifying that existing behavior through a Settings control, not inventing theme support from zero. Settings itself is still a static placeholder (`js/pages/settings/settings-page.js`) with no such control wired up yet.
- **Automatic Week, Personnel Directory, and Google Sheet personnel sync do not exist today.** Report's "Week" field (V2.0 doc, Section 10.1) is manual free text; there is no personnel data model anywhere in the repository.
- **V2.3 does not claim byte-identical report output.** Report Output Migration (Section 19) intentionally changes the personnel section of the generated report — SPV SCM, FRM SCM, Independent Sampler, and PIC 3rd replace the current PIC/Manpower free-text lines (Section 19.5). Only the non-personnel sections (calculations, buyer labels, loading areas, Daily/WTD/MTD/YTD) are required to remain unchanged.
- **Offline licensing cannot provide absolute tamper resistance in a public static application.** This is a client-side PWA served from GitHub Pages with no backend; a technically capable person can modify the public JavaScript or run a modified local copy — with the Phase 8 design below, such a person can also read the (non-secret) PBKDF2 verifier directly from the shipped bundle and craft a matching `hpal.license.v1` entry without ever knowing the real key. This document does not claim unbreakable DRM, server-grade authorization, or authenticated user identity anywhere below; Phase 8's own security-limitations section (Section 9) states this explicitly.
- **(Phase 8 licensing update, 2026-08-08) No private signing key or license-generation secret may ever be committed to this repository**, embedded in shipped JavaScript, cached by the service worker, or written to the personnel Google Sheet. This still applies under the simplified design even though there is no longer any asymmetric key pair: the plaintext access key itself must never be committed, embedded, or cached — only its PBKDF2 verifier (a one-way derived value) may be.
- **V2.2 remains the currently implemented and deployed release.** V2.3 is the planned target version this document describes.

## Section 5 — Application Routing Changes

`router.js` (V2.0 §4, unchanged through V2.1/V2.2) exposes exactly `ROUTE_PATTERN = /^#\/(monitor|report|settings)$/`, with unknown/empty hashes redirected to `monitor`. V2.3 does not add or rename any route. It adds a **guard layer** in front of the existing three:

- `router.js` gains `registerRouteGuard(route, guardFn, onDeny)`, called by `applyRoute()` immediately after a route is resolved and before its page is shown. `guardFn(route)` returns `true` (allow) or `false` (deny); on deny, `applyRoute()` calls the guard's own `onDeny(route)` instead of activating the requested page — the guard itself owns the redirect behavior (there is no generic "fallback route" parameter on the router), so it can perform whatever multi-step deny action it needs (redirect + focus a specific card + show a message), not just a bare route change.
- `app.js` registers exactly one guard at bootstrap: `report` → allowed only when `licenseService.hasFullAccess()` is `true`; on deny, the guard **always** performs the same deterministic sequence — never to `#/monitor`, never an unspecified "unlock explanation" — it navigates to `#/settings` and calls `licenseService.requestFullAccessAttention()`, which `settings-page.js` subscribes to in order to open/focus the License card and show the "Fitur ini memerlukan Lisensi Akses Penuh." / "This feature requires a Full Access License." message (Section 10) once `#/settings` actually becomes the active route. This is the one and only unlicensed-`#/report` behavior; no alternate path exists.
- `monitor` and `settings` are never route-guarded — `settings` opens in both tiers, restricted internally per Section 20, not by the router.
- This is a route-level guard only. Section 10 requires every licensed action to *also* verify access at the action boundary (e.g. inside Report's own step-gating functions), so a route guard bypass (calling a Report function directly from DevTools) is still blocked independently.
- If a license is removed (Settings' Remove License action) while `#/report` is already the active route, no route change occurs on its own to re-trigger the guard above — `app.js` additionally subscribes to `licenseService.subscribeAccessChange()` and explicitly navigates to `#/settings` if the current route is `report` at the moment access drops to `MONITOR_ONLY`.

## Section 6 — License and Access Architecture

> **Phase 8 licensing update (2026-08-08):** Sections 6–11 originally described an asymmetric signed-offline-token architecture with an external License Generator (ECDSA P-256 signing, a `HPALLIC1.<payload>.<signature>` token format). The Owner explicitly decided **not** to build that for V2.3 and approved the simpler design below instead: one permanent, Owner-held local access key, verified locally via PBKDF2-HMAC-SHA-256. This is the current, implemented V2.3 design. The signed-token approach may still be revisited as a future upgrade if stronger guarantees are ever needed, but it is not part of V2.3.

### 6.1 Access states

Two application-wide access states, with a stable machine identifier and Indonesian/English display names:

| Internal identifier | Indonesian display name | English display name |
| --- | --- | --- |
| `MONITOR_ONLY` | Akses Monitor | Monitor Access |
| `FULL_ACCESS` | Lisensi Akses Penuh | Full Access License |

`FULL_ACCESS` is the stable machine identifier for the licensed tier — never a vague name like `user`. `MONITOR_ONLY` is the implicit default state whenever no valid license is installed; it is never itself stored as a token, only derived.

### 6.2 `MONITOR_ONLY` access

Available without any license:
- Monitor page, Monitor Excel upload, Monitor calculations, Monitor charts, existing Monitor contractor synchronization.
- Local language selection, local appearance selection.
- The License input required to unlock the application.

Unavailable without a valid license:
- Report (all buyers: HYNC, SLNC, ESG Format A, ESG Format B).
- Personnel Directory management.
- Google Sheet personnel write actions.
- Any future feature explicitly assigned to `FULL_ACCESS`.

**Settings exception, documented explicitly because License/Language/Appearance controls live inside Settings:** the Settings route (`#/settings`) may still be opened in `MONITOR_ONLY` mode, but only three of its sections are available — License, Language, Appearance. Role & Personnel Directory, personnel synchronization writes, and future licensed operational settings remain locked (Section 20 has the full per-tier table). "Monitor only" therefore means *operational* access is limited to Monitor, while the restricted Settings controls needed to unlock and configure the local application remain reachable. An unlicensed user must never be redirected away from the License input.

### 6.3 `FULL_ACCESS` license

A valid `FULL_ACCESS` license unlocks: Monitor, Report HYNC, Report SLNC, Report ESG Format A, Report ESG Format B, Personnel Directory, personnel synchronization, licensed Settings functions, and any future feature explicitly assigned to `FULL_ACCESS`. The access tier is application-wide — V2.3 does not create separate HYNC/SLNC/ESG licenses.

### 6.4 History: the Phases 2–7 build had no license gate at all

Unlike the original plan (which assumed Report and the Personnel Directory would be built behind a temporary development bypass, then gated in Phase 8), Phases 1–7 were in fact built and shipped on `main` with **no access gate whatsoever** — every feature was reachable by anyone, always. Phase 8 (this update) is the first point at which any gate exists. There was therefore never a development bypass to build, label, or later remove; a repository-wide search for one (Section 22/28) is expected to find nothing, and that is the correct, expected result — not evidence of an incomplete removal.

## Section 7 — Local Access-Key Verification

The Owner requires licensing to work without internet access and without any external license-generation tooling, so verification is entirely local, using exactly one permanent access key.

### 7.1 Approved architecture direction

1. The Owner holds exactly one access key — a fixed passphrase-style string, generated and communicated outside the application (there is no in-app "generate a license" flow, and no per-installation/per-customer license identifier).
2. The application never stores or embeds the plaintext key. It embeds a **PBKDF2-HMAC-SHA-256 verifier** derived from the key, plus the salt and iteration count used to derive it.
3. The user enters the key once, in Settings; the application derives the same verifier locally, using the **Web Crypto API** (`crypto.subtle`), and compares it byte-for-byte against the embedded verifier.
4. On a match, a local **proof** (the derived verifier bytes themselves, base64-encoded) is stored — never the plaintext key, and never anything that can recover it.
5. Every subsequent app start re-validates the stored proof against the embedded verifier; no network connection is required at any point.

### 7.2 Verification parameters (as implemented, `js/services/license-service.js`)

| Parameter | Value | Notes |
| --- | --- | --- |
| Algorithm | PBKDF2 | Via `crypto.subtle.importKey('raw', ..., 'PBKDF2', false, ['deriveBits'])` + `crypto.subtle.deriveBits(...)` — no custom/hand-rolled crypto. |
| Hash | SHA-256 | |
| Iterations | 210,000 | A reasonable browser-safe baseline for a single, interactive, client-side verification (not a server-side password-hashing workload) — see the constant's own comment in `license-service.js` for the OWASP-baseline comparison and why it does not directly apply here. |
| Derived key length | 256 bits (32 bytes) | |
| Salt | A fixed, application-specific 16-byte value, generated once via a CSPRNG and stored base64-encoded in source | Public by design — a PBKDF2 salt is not a secret, it only needs to be fixed and unique to this verifier. |
| Verifier version | `1` (`verifierVersion`) | Bumping this constant invalidates every previously-installed local proof, forcing re-entry — the mechanism Section 8 relies on if the verifier parameters ever need to change. |

Comparison of the derived bytes against the embedded expected verifier is constant-time-ish (always walks the full, equal-length byte array rather than short-circuiting on the first mismatch), so a timing side-channel cannot meaningfully narrow down the correct key.

**Input handling:** the entered key is used exactly as typed — never trimmed, never case-normalized. A single leading/trailing space or a case difference produces a different derived verifier and therefore fails. The input is cleared immediately after every verification attempt (success or failure) and is never logged, never placed in an exception message, and never written to `localStorage`/`sessionStorage`/IndexedDB/the service worker cache in plaintext form.

### 7.3 What may and may not be embedded in the public application

**Safe to distribute publicly** (this is a one-way derived value, not a secret):
- The verification algorithm (this document, and the shipped `license-service.js` source).
- The salt, iteration count, derived-key length, and verifier version.
- The expected verifier itself (a PBKDF2 output — cannot be used to recover the plaintext key).

**Must never be embedded, committed, or cached:**
- The plaintext access key, in any form — source, comments, tests, docs, commit messages, or screenshots/logs.
- Any reversible ciphertext of the key.
- Any encryption key or mechanism capable of recovering the plaintext key from the stored verifier.

The plaintext key may only ever exist as local, temporary input: while an engineer generates the verifier constant offline (never committed alongside it), and while the Owner manually types it into the running application during testing. A repository-wide search must prove it is absent from every tracked file before release (Section 28).

### 7.4 Startup verification sequence

1. Read the stored `hpal.license.v1` record from local storage (Section 8).
2. Validate its shape: `schemaVersion`, `verifierVersion` (must match the currently-embedded verifier version), and a well-formed `proof`.
3. Compare `proof` against the embedded expected verifier.
4. Derive the current access tier (`FULL_ACCESS` only if steps 2–3 both succeed; `MONITOR_ONLY` otherwise, with any invalid/corrupted record actively removed rather than left in place).
5. Apply route and feature guards (Section 10) based on the derived tier.

A cached boolean such as `isLicensed: true` is never trusted by itself — every load re-runs steps 1–4 against the raw stored record, and step 2–3's actual proof comparison is what determines the tier, not the mere presence of a record.

## Section 8 — License Storage

Local-storage namespace, as implemented:

```text
hpal.license.v1
```

Stored shape, as implemented (`js/services/license-service.js`):

```json
{
  "schemaVersion": 1,
  "verifierVersion": 1,
  "proof": "<base64 PBKDF2 verifier bytes>",
  "installedAt": "2026-08-08T01:00:00.000Z",
  "lastVerifiedAt": "2026-08-08T01:00:00.000Z"
}
```

- `proof` is the derived verifier itself (one-way, never reversible to the plaintext key) — the only field the startup sequence (Section 7.4) actually trusts; `installedAt`/`lastVerifiedAt` are conveniences for the Settings UI, not trust anchors.
- Because this is a static client-side PWA with no backend, this local proof is **not a strong tamper-proof trust anchor** — a technically capable user can read the (non-secret) expected verifier directly from the shipped bundle and write a matching `proof` into their own browser storage, reaching `FULL_ACCESS` without ever knowing the real key. This is an accepted, explicitly documented limitation (Section 9), not an oversight; it is exactly as strong as any purely client-side gate can be, no stronger and no weaker.

### 8.1 Removal behavior

When the local license is removed (user action via Settings' "Remove License", or a corrupted/invalid record detected at startup):
- The application immediately returns to `MONITOR_ONLY`.
- Licensed operational pages are closed or redirected away from (Section 10) — if `#/report` was the active route, it redirects to `#/settings`.
- Settings itself re-renders into its restricted three-section (License/Language/Appearance) shape.
- Unrelated Monitor data, local preferences (language, appearance), the Personnel Directory cache, and any pending offline personnel write queue items are **not** deleted — the cache and queue simply become inaccessible/dormant through Settings' UI and action guards (Section 16.5) until `FULL_ACCESS` is restored, rather than being erased.

### 8.2 Storage-loss / re-entry behavior

The key must be entered again only after: an explicit Remove License; browser/site storage being cleared; PWA storage loss or reinstall; the embedded `verifierVersion` changing (Section 7.2); or a corrupted/invalid stored record. In every other case (normal reload, PWA relaunch, offline restart), a previously-verified proof restores `FULL_ACCESS` automatically, with no re-entry and no network required. This is accepted as the V2.3 baseline — no server-side recovery exists, since there is no server.

## Section 9 — License Security and Limitations

Stated explicitly, per the Owner's requirement:

> HPAL Production Monitor is a static public client-side PWA. A local access-key gate can prevent casual/unintended access and keep the plaintext key out of source control, but it cannot provide absolute tamper resistance against a technically capable person who modifies the public JavaScript, inspects the shipped bundle, or runs a modified local copy.

Therefore, this document and any implementation built from it must not:
- Claim unbreakable DRM.
- Claim server-grade authorization.
- Describe hidden UI (e.g. a hidden bottom-navigation item) as security.
- Claim the verifier/salt/iteration-count being public is itself a weakness to hide — Section 7.3 already requires them to be assumed public; obscuring them would add nothing.

This local access-key gate is the Owner-approved V2.3 design specifically because it is simple, works fully offline, requires no external tooling or backend, and keeps the plaintext key out of the repository — not because it is unbreakable. Route guards and feature guards must both exist (Section 10); a hidden Report navigation item alone is insufficient.

## Section 10 — License Route and Feature Guards

| Route/action | `MONITOR_ONLY` | `FULL_ACCESS` |
| --- | --- | --- |
| `#/monitor` | Allowed | Allowed |
| `#/report` | Blocked; always redirected to `#/settings` with the License card opened/focused and the Full Access requirement message shown (Section 5) — never to `#/monitor` | Allowed |
| `#/settings` | Allowed, restricted mode (Section 20) | Allowed, fully |
| Report module actions invoked programmatically (Step 1→2, Step 2→3/Generate, workbook upload) | Blocked at the action boundary, independent of the route guard | Allowed |
| Personnel Directory reads/writes/sync (Settings UI or invoked programmatically) | Locked, independent of Settings UI visibility | Allowed |
| Offline personnel write queue flush/retry (startup, `online` event, or manual Sync) | Blocked at the queue-flush action boundary itself — pending items remain dormant, never attempted, never marked blocked by this alone | Allowed; queue behavior resumes normally |
| Licensed UI controls | Not rendered at all (Personnel Directory section) or not present in the nav (Report) — never merely disabled | Rendered and enabled |

Each licensed action independently verifies access at the action boundary via `licenseService.hasFullAccess()` — implemented as one reusable guard per module rather than scattered ad hoc checks: `report-page.js`'s `requireFullAccessForReportAction()` (used by `goToStep2()`/`goToStep3()`, which already gate on buyer confirmation per V2.1 §8, and by the workbook-upload handler), and independent `hasFullAccess()` checks inside `personnel-directory-service.js`'s sync/add/update/setActive functions and `personnel-write-queue.js`'s flush/retry functions. Relying only on bottom-navigation visibility or the route guard is insufficient — both must exist, per Section 9.

**Blocked-access message**, shown wherever a licensed action or route is denied:

- Indonesian: *Fitur ini memerlukan Lisensi Akses Penuh.*
- English: *This feature requires a Full Access License.*

Every occurrence of this message is paired with a direct action: the route guard and the Report action guard both navigate to `#/settings` and request the License card be opened/focused (`licenseService.requestFullAccessAttention()`, subscribed to by `settings-page.js`) — never a dead end.

## Section 11 — License Permanence and Portability

**V2.3 baseline, as implemented: permanent local key, no expiration, no device binding.**

Reasons, recorded as architecture decisions rather than assumptions:
- Offline expiration depends on the local device clock, which users may (accidentally or otherwise) change.
- Browser/PWA device identifiers are unstable across browser resets, OS updates, and reinstalls.
- Device binding risks locking out a legitimate user after a reinstall, browser reset, or OS change, with no server-side recovery path to fall back on.
- There is no server, so no expiration or device-binding check could be enforced server-side even if one were added client-side (a client-side-only check is trivially bypassable, per Section 9).

The stored record (Section 8) carries no `expiresAt` or device-identifier field at all in V2.3 — unlike the original signed-token draft, which reserved (but did not rely on) such fields, this design does not include them, since there is no token payload to reserve fields within. A future upgrade could add them, but that is out of scope here.

**License portability:** the same access key may be re-entered after browser storage loss, on the same or a different device; V2.3 has no mechanism to prevent this, and any distribution-restriction policy remains an Owner operational responsibility.

## Section 12 — Language and Localization

### 12.1 Settings card

**Language**
- Options: Bahasa Indonesia / English.
- Stable internal locale identifiers: `id`, `en`.
- Default locale: `id`.
- Works fully offline; no server synchronization required.

### 12.2 Localization architecture

```text
js/i18n/
  i18n.js
  locales/
    id.js
    en.js
```

- `i18n.js` — current-locale state, `t(key, vars?)` translation lookup, fallback handling, and a small UI-update hook (re-render subscribers on locale change) so already-rendered pages update in place rather than requiring a reload.
- `locales/id.js` / `locales/en.js` — flat or lightly-nested key→string maps.

Stable translation keys are required everywhere UI text is localizable — conditionals such as `if (language === 'id')` scattered through Report/Settings code are explicitly disallowed by this architecture. Representative keys (not exhaustive):

```text
nav.monitor
nav.report
nav.settings
settings.license.title
settings.language.title
settings.appearance.title
personnel.spvScm
personnel.frmScm
personnel.independentSampler
personnel.picThirdParty
license.fullAccessRequired
common.sync
common.add
common.edit
common.deactivate
```

**Fallback behavior:** if the selected locale is missing a key, fall back to Indonesian; optionally log a development-only console warning; never render an empty string or a raw key name to the user.

### 12.3 Language scope

V2.3's target UI translation scope: app shell, bottom navigation, Report, Settings, personnel selectors, sync status, validation messages, license messages, common buttons.

**Generated operational report text is explicitly excluded from UI localization.** Changing the application's UI language must never automatically translate or alter HYNC/SLNC output format, ESG Format A/B output format, operational labels copied into the WA report, or the spacing/punctuation the approved report profiles already produce (V2.1 §11, V2.2 §10). UI language is localizable; generated operational report text remains controlled by the approved report profile format, independent of the active UI locale.

### 12.4 Monitor legacy-string inventory requirement

Monitor (`index.html`) contains substantial legacy inline UI text that predates this i18n architecture. Before any implementation of V2.3 claims complete application-wide bilingual support, that implementation must first inventory Monitor's strings. If full Monitor translation cannot be completed safely within the same phase, it must be documented as a staged migration (i.e., Monitor UI stays Indonesian-only for one more release while the rest of the app is bilingual) rather than shipping an undocumented mixture of translated and untranslated UI. This is recorded as an open decision in Section 29, not resolved here.

## Section 15 — Automatic Week Architecture

**Current behavior (V2.0 §10.1, unchanged through V2.2):** Report Step 1's "Week" field is manual free text, entered independently of the uploaded workbook's date.

**V2.3 behavior — authoritative, Owner-approved, not an open question:**

- **Week starts on Monday and ends on Sunday.**
- **Week numbering follows ISO week-number behavior** (the ISO-8601 definition: weeks run Monday–Sunday, and week 1 of a year is the week containing that year's first Thursday).
- **Week is calculated from the active workbook's date**, never from the device's current date, whenever a workbook date exists. Once a workbook has been parsed and its `fileDate` is known (already produced by every existing parser — `shared-report-profile.js`'s `parseWeighbridgeWorkbook()` and both ESG adapters all return a `fileDate`, per V2.1 §12 and V2.2 §3), Report computes the week from that value, via a new, buyer-agnostic helper (proposed: `computeOperationalWeek(fileDate)` in `report-utils.js`, since `report-utils.js` is already the shared, buyer-agnostic formatting/parsing home per V2.1 §5).
- **The Week field is read-only in V2.3.** There is no manual override — the UI renders the computed value as display text (or a disabled/read-only input), not an editable field.
- **Replacing the uploaded workbook recalculates Week** from the new file's date. Because there is no manual edit to preserve (Week is read-only), recomputation on every successful parse is unconditional — there is no re-fill-vs-preserve-edit ambiguity to resolve.
- **An invalid or unparseable workbook date blocks Report progression.** If `fileDate` cannot be determined from the uploaded workbook, `computeOperationalWeek()` cannot run, and the Step 1→2 gate (`goToStep2()`, V2.1 §10) must add a blocking error to the same validation list HYNC/SLNC/ESG's other Step 1 checks already use — Report does not silently proceed with a missing or device-derived Week value.

### 15.1 Stored fields

`computeOperationalWeek(fileDate)` returns, and Report state stores, four fields (also listed in Section 19.3's full Report-state table):

| Field | Meaning |
| --- | --- |
| `weekNumber` | ISO week number (1–53) derived from the workbook date |
| `weekYear` | ISO week-numbering year (which can differ from the calendar year for dates in the first/last days of December/January, per ISO-8601) |
| `weekStart` | The Monday that begins the ISO week containing the workbook date |
| `weekEnd` | The Sunday that ends that same ISO week |

Storing all four — not just a single display string — lets the UI render "Week 32 (2026-08-03 – 2026-08-09)" or an Indonesian-localized equivalent without re-deriving the boundary dates at render time, and keeps `weekYear` correct across ISO year-boundary weeks without relying on the calendar year alone.

## Section 16 — Personnel Directory Architecture

**Correction from an earlier draft of this document:** an earlier version of this section proposed a single generic person record with a `roles: []` array as the primary data model, mirroring V2.0 §15.1's original sketch. That generic-person-with-roles-array shape is **not** the approved model and must not be used as the primary Google Sheet or local-cache model. The approved model is one directory record per role type per person/organization (Section 16.1), matching one authoritative Sheet tab (Section 16.3).

### 16.1 Approved role model

Exactly four stable role types — no more, no fewer, in V2.3:

| Role type (`role_type`) | Indonesian label | English label |
| --- | --- | --- |
| `SPV_SCM` | SPV SCM | SPV SCM |
| `FRM_SCM` | FRM SCM | FRM SCM |
| `SAMPLER` | Independent Sampler | Independent Sampler |
| `PIC_3RD` | PIC 3rd | PIC 3rd |

These four replace every role identifier proposed in an earlier draft of this document — `PIC_SCM`, `PIC_PARTNER` (dynamic AWK/ATQ label), `INDEPENDENT_SAMPLER`, and `PIC_THIRD_PARTY` are **not** used as directory role identifiers. `SAMPLER` and `PIC_3RD` cover the buyer-partner concept instead (Section 19.2 defines exactly how).

### 16.2 Record shape

One directory record represents one role instance for one person/organization — not one person holding multiple roles in an array:

```js
{
  id: 'person-001',
  role_type: 'SPV_SCM',
  name: 'Illofi',
  organization: 'SCM',
  active: true,
  created_at: '2026-08-06T01:00:00Z',
  updated_at: '2026-08-06T01:00:00Z',
  updated_by: 'settings-ui',
  version: 1
}
```

**Role and organization behavior:**

| Role type | `organization` value |
| --- | --- |
| `SPV_SCM` | Always `SCM` |
| `FRM_SCM` | Always `SCM` |
| `SAMPLER` | The sampler organization itself (e.g. `AWK`, `ATQ`) — `name` and `organization` are effectively the same identity for this role type |
| `PIC_3RD` | Identifies which sampler the PIC belongs to (e.g. La Ode Osardi → organization `AWK`; Khalifa Akbar → organization `ATQ`) |

A person who is, say, both an SPV SCM and an FRM SCM is represented as **two separate records** (one `SPV_SCM`, one `FRM_SCM`), not one record with two roles — this is the direct consequence of rejecting the roles-array model above, and it is what lets Section 16.3's per-role uniqueness rules and Section 20's four independent Settings cards each own exactly one record type.

### 16.3 Google Sheet data model

The authoritative Google Sheet tab is:

```text
report_personnel
```

Row model (one row per directory record, per Section 16.2's shape):

```text
id | role_type | name | organization | active | created_at | updated_at | updated_by | version
```

**Uniqueness rules**, enforced both client-side (before queueing a write) and server-side (in the Apps Script write handler, so two offline clients can't both "successfully" create the same logical record):

| Role type | Uniqueness key |
| --- | --- |
| `SPV_SCM` | `role_type` + normalized `name` |
| `FRM_SCM` | `role_type` + normalized `name` |
| `SAMPLER` | `role_type` + normalized `organization` |
| `PIC_3RD` | `role_type` + normalized `name` + normalized `organization` |

"Normalized" means trimmed, whitespace-collapsed, and case-folded for comparison — the same normalization discipline `contractor-adapter.js`'s `normalizeDtKey()` already applies to DT ids (V2.1 §14) — display casing (`name`/`organization` as entered) is preserved in the stored record; only the comparison key is normalized.

`version` is an optimistic-concurrency counter, incremented on every accepted write, so a write against a stale `version` can be detected as a conflict (Section 18) rather than silently overwriting a concurrent edit.

### 16.4 Local cache

```text
hpal.personnel.v1
```

```json
{
  "schemaVersion": 1,
  "records": [
    { "id": "person-001", "role_type": "SPV_SCM", "name": "Illofi", "organization": "SCM", "active": true, "created_at": "...", "updated_at": "...", "updated_by": "...", "version": 1 }
  ],
  "lastSyncedAt": "2026-08-06T01:00:00Z"
}
```

The local cache mirrors the Sheet's row model directly (Section 16.3) — it is a cache of `report_personnel`, not a separately-shaped convenience model. A UI layer may derive per-role or per-organization groupings (e.g. "all active `PIC_3RD` records for organization `AWK`") from this flat `records` array at render time, but the array itself, and the Sheet it mirrors, remain the one-record-per-role-instance model.

### 16.5 Settings CRUD (licensed)

Personnel management is **four separate directory cards**, one per role type, not one generic undifferentiated personnel card — the exact card layouts are specified in Section 20.6, not here, since they are a Settings-page concern. Each card provides: an active-record count, an add form scoped to that role type's fields, a Sync action, and an active/inactive list with Edit and Deactivate/Reactivate — never hard-delete, so historical report attribution stays intact after someone leaves a role.

Personnel management (all four cards, both reads and writes) is available **only** under `FULL_ACCESS` (Section 6.2) — the spec explicitly lists "Personnel Directory management" (not only "writes") as an operational page unavailable without a license.

## Section 18 — Google Sheet Personnel Sync — Write (Online First), Then the Optional Offline Write Queue

**Correction from an earlier draft of this document:** an earlier version presented online write-sync and the offline write queue as one combined, already-proven precedent. They are not built together in V2.3. Per the Owner-approved phasing (Section 22), **online add/edit/deactivate/reactivate writes ship first and must be stable on their own (Phase 4) before the optional offline write queue is added on top (Phase 5)**. `contractor-assignment.js`'s existing queue is a useful structural precedent for the *shape* of an offline queue, but it is not proof that personnel conflict semantics are already solved — personnel records have per-role uniqueness rules and a `version` field (Section 16.3) that the contractor list does not, so conflict handling needs its own dedicated validation, not an assumption that the contractor pattern transfers unchanged.

### 18.1 Phase 4 — online writes

Add/edit/deactivate/reactivate actions from the four Settings cards (Section 20.6) call the Apps Script `upsertPersonnel` (or equivalent) action directly while online:

- `POST` with `action: 'upsertPersonnel'`, `Content-Type: text/plain;charset=utf-8` (avoiding a CORS preflight against the Apps Script endpoint, the same trick `contractor-assignment.js` already uses), JSON body of one record patch, including its current `version`.
- The server rejects a write whose `version` doesn't match the row's current `version` (a concurrent edit happened first) as a conflict, not a silent overwrite — this is the dedicated validation the uniqueness rules in Section 16.3 require, and it does not exist in the contractor-sync precedent, which has no `version` field at all.
- A uniqueness violation (Section 16.3's per-role key) is rejected with a clear error, surfaced in the originating card (Section 20.6), not queued for later retry.
- `fetchPersonnelDirectory()` (Section 17) is re-run after a successful write to refresh the authoritative list, mirroring `fetchExistingContractors()`'s existing re-fetch-after-sync behavior.
- Write access is licensed (Section 6.3): the contractor-sync write flow today has no license gate at all (V2.0/V2.1/V2.2 predate licensing entirely); personnel writes must check `FULL_ACCESS` at the action boundary before sending anything, per Section 10 (subject to Section 6.4's temporary development bypass before Phase 8).

**Do not describe offline writes as mandatory or already proven for this first personnel release** — Phase 4's acceptance bar is: online add/edit/deactivate/reactivate work correctly, including conflict and uniqueness rejection, with no offline queue involved at all.

### 18.2 Phase 5 — optional offline write queue (only after Phase 4 is stable)

Once Phase 4's online writes have shipped and been verified, an offline write queue may be added, structurally informed by `contractor-assignment.js`'s existing queue but validated independently for personnel's stricter data model:

| Concern | Existing contractor precedent (structural reference only) | V2.3 personnel equivalent |
| --- | --- | --- |
| Local queue key | `hpal-unmatched-contractor-queue-v1` (`localStorage`) | `hpal.personnel-write-queue.v1` |
| Queue shape | Array of `{ dt_id, contractor, saved_at }`, deduplicated by a normalized key on every write (`writeQueue()`) | Array of `{ recordId, roleType, patch, baseVersion, savedAt }` — `baseVersion` lets the server detect a conflict the same way Phase 4's direct writes already do |
| Optimistic local save | `upsertQueue()` writes immediately to `localStorage`; the UI marks the row "Tersimpan lokal, menunggu sinkron" before any network call | Same pattern: a Settings edit is saved to the local cache and the write queue synchronously, marked pending, before any network call |
| Sync trigger | Manual "Simpan & Sinkron" button, plus an automatic `window.addEventListener('online', () => syncPending(true))` silent retry | Same: a manual "Sync now" action per card (Section 20.6), plus the same `online` event listener for automatic flush |
| Conflict/error handling | Server response distinguishes `appended`/`updated_blank`/`duplicate_skipped`/`conflicts`/`errors`; only successfully-processed keys are removed from the local queue | Same reporting shape, but conflicts are evaluated against `baseVersion` and Section 16.3's uniqueness keys specifically — a case (two offline devices editing the same `PIC_3RD` record) that has no equivalent in the contractor precedent and must be tested on its own (Section 26), not assumed safe by analogy |

The contractor queue remains a useful precedent for *how* to structure an offline queue (local-first save, optimistic UI, automatic online-event flush) — it is not a substitute for validating personnel's own conflict and uniqueness rules, which this document treats as unproven until Section 26's test matrix passes against the actual implementation.

### 18.3 What is genuinely new relative to the contractor precedent

- The **UI surface** is new: `contractor-assignment.js`'s modal is triggered by detecting unknown DT ids in an uploaded workbook; personnel management is four deliberate Settings CRUD cards (Section 20.6), not a reactive "unknown item found" popup.
- **Conflict semantics are new**: the contractor list has no `version` field and no per-role uniqueness key; personnel's Phase 4 writes and Phase 5 queue both depend on `version`-based conflict detection that must be built and tested from scratch.
- The **Apps Script endpoint** is new infrastructure (or a new action on existing infrastructure) targeting `report_personnel` — the exact deployment shape is an implementation-time, Owner-side decision (Section 29), not something this document can finalize without access to the Owner's Google Apps Script project.

## Section 19 — Report Output Migration

**Correction from an earlier draft of this document:** an earlier version claimed this migration was a UI-layer-only change producing unchanged `buildReportText()` output, with a text-input escape hatch if the Personnel Directory was unavailable. Neither claim is correct. **V2.3 intentionally changes the personnel section of the generated report's text** (Section 19.5), and **Report must never allow typed-in, ad hoc person creation** (Section 19.4) — an unavailable directory is a blocking validation state, not a reason to degrade to text input.

### 19.1 New Report fields and selection behavior

Once the Personnel Directory (Section 16) and its sync (Sections 17–18) are stable, Report's Man Power section (V2.0 §10.1's PIC SCM/PIC AWK/Manpower AWK/Total Manpower fields, unchanged through V2.2) is replaced by:

| Field | Selection mode | Source |
| --- | --- | --- |
| SPV SCM | Multi-select | Active `SPV_SCM` records only |
| FRM SCM | Multi-select | Active `FRM_SCM` records only |
| Independent Sampler | Single-select | Active `SAMPLER` records |
| PIC 3rd | Multi-select | Active `PIC_3RD` records, filtered to those whose `organization` matches the currently selected sampler |
| Manpower 3rd | Numeric input | Not personnel-directory-backed; the field's **output label** follows the selected sampler (`Manpower AWK` / `Manpower ATQ`) |
| Total Manpower | Numeric input | Unchanged field, revalidated against Manpower 3rd (Section 19.4) |

**No free-text person creation inside Report, under any condition.** New personnel are created only through the Settings cards (Section 20.6). If there is no valid personnel directory cache (first run before any sync, or a corrupted/expired cache), Report shows a blocking validation message directing the user to Settings — it does not silently fall back to free-text inputs for SPV SCM, FRM SCM, Independent Sampler, or PIC 3rd.

**When Independent Sampler changes** (user action, or a buyer-driven default change per Section 19.2):
1. PIC 3rd selections whose `organization` no longer matches the new sampler are cleared.
2. PIC 3rd selections that remain compatible (same `organization` as the new sampler) are preserved.
3. A non-destructive information message explains what was cleared and why.
4. The Manpower label updates immediately (`Manpower AWK` ↔ `Manpower ATQ`).
5. Any already-generated report output is invalidated (mirroring how a buyer-mismatch already clears `reportState.reportText`, V2.1 §8) — a stale report under the wrong sampler/PIC combination cannot survive the change.

### 19.2 Buyer default sampler

| Buyer | Default sampler |
| --- | --- |
| HYNC | AWK |
| SLNC | AWK |
| ESG | ATQ |

The user may override the default at any time. Report tracks whether the current sampler selection came from `default` (auto-applied) or `user` (a deliberate choice) — stored as `samplerSelectionSource` (Section 19.3).

**When the resolved buyer changes** (V2.1 §7–§8's buyer-resolution state machine):
1. The new buyer's default sampler is applied **only if** `samplerSelectionSource === 'default'` — a user's deliberate override is never silently replaced by a buyer-driven default.
2. If the selection source is `user` and the previously chosen sampler is still valid (active, exists), it is preserved as-is across the buyer change.
3. PIC 3rd selections are revalidated against whichever sampler is now in effect; incompatible selections are cleared per Section 19.1's five-step rule.
4. Generated output is invalidated, same as a direct sampler change.

### 19.3 Report state fields (proposed additions to `report-state.js`)

| Field | Purpose |
| --- | --- |
| `weekNumber` | ISO week number, from Section 15.1 |
| `weekYear` | ISO week-numbering year, from Section 15.1 |
| `weekStart` | Monday of the computed ISO week, from Section 15.1 |
| `weekEnd` | Sunday of the computed ISO week, from Section 15.1 |
| `selectedSpvScmIds` | Array of selected `SPV_SCM` record ids |
| `selectedFrmScmIds` | Array of selected `FRM_SCM` record ids |
| `selectedSamplerId` | Selected `SAMPLER` record id |
| `samplerSelectionSource` | `'default'` or `'user'` (Section 19.2) |
| `selectedPic3rdIds` | Array of selected `PIC_3RD` record ids |
| `manpower3rd` | Numeric Manpower 3rd input |
| `totalManpower` | Numeric Total Manpower input |
| `personnelDirectoryVersion` | A snapshot marker (e.g. the local cache's `lastSyncedAt` or a content hash) identifying which directory snapshot the current selections were made against |

**Stable ids, not just display names, are stored** — `selectedSpvScmIds` etc. hold `report_personnel` record ids (Section 16.3), and names/labels for rendering and for `buildReportText()` (Section 19.5) are always looked up live from the current personnel directory, never cached as plain strings inside `reportState`.

**When a selected record becomes inactive or disappears after a sync** (deactivated in Settings, or removed from `report_personnel` entirely): Report retains enough identity (the stored id, and the last-known name/organization from before the sync) to show the user exactly which selection became invalid, blocks report regeneration until the user corrects it, and never silently substitutes a different, still-active person in its place.

### 19.4 Personnel validation

**Blocking** (Report cannot progress past the relevant step):
- Week cannot be calculated (Section 15 — invalid/unparseable workbook date).
- No active SPV SCM selected.
- No active FRM SCM selected.
- No Independent Sampler selected.
- No active PIC 3rd selected.
- A selected PIC 3rd's `organization` does not match the selected sampler.
- A selected record (any of the four role types) is inactive or missing from the current directory (Section 19.3).
- Manpower 3rd is invalid (non-numeric, negative, or otherwise out of range).
- Total Manpower is invalid.
- Total Manpower is less than Manpower 3rd.
- No valid personnel directory cache exists at all (Section 19.1).

**Non-blocking** (surfaced as a warning, Report may still proceed):
- Operating in offline mode using a valid cached directory.
- A stale-cache warning (the local snapshot is older than some freshness threshold, but still structurally valid).
- The user's sampler selection differs from the current buyer's default (`samplerSelectionSource === 'user'`) — this is an expected, deliberate state, not an error.
- A personnel write is pending sync (Section 18).

### 19.5 Report output change

**The personnel section of the generated report is intentionally different from V2.2's output — this is not a byte-identical migration.** Calculations and every non-personnel report section (Daily/WTD/MTD/YTD, buyer labels, loading areas, and all other approved output, V2.1 §11/§13, V2.2 §10) remain unchanged; only the personnel lines change shape.

**Target personnel output, HYNC/SLNC example (sampler = AWK):**

```text
SPV SCM             : Illofi, Yoshita
FRM SCM             : Adi Guna
Independent Sampler : AWK
PIC 3rd              : La Ode Osardi
Manpower AWK         : 25
Total Manpower       : 27
```

**Target personnel output, ESG example (sampler = ATQ):**

```text
SPV SCM             : ...
FRM SCM             : ...
Independent Sampler : ATQ
PIC 3rd              : Khalifa Akbar
Manpower ATQ         : 15
Total Manpower       : ...
```

Requirements on this new output shape:
- SPV SCM and FRM SCM are shown on **separate lines** — they are never merged into one combined line.
- Independent Sampler is shown **explicitly** as its own line (it was implicit in the buyer's partner label before V2.3; it is now a first-class output line).
- **PIC 3rd replaces** the previous PIC AWK/PIC ATQ line entirely — there is no PIC AWK/PIC ATQ line in V2.3 output.
- The Manpower output label follows the selected sampler (`Manpower AWK` or `Manpower ATQ`), per Section 19.1.
- Multiple selected names on one line (SPV SCM, FRM SCM, or PIC 3rd with more than one selection) are **comma-separated**.
- Output ordering is **deterministic** — the same set of selected ids always renders in the same order (e.g. by the order records were selected, or by a stable sort on the underlying directory, whichever the implementation picks — but it must be a fixed, documented rule, not insertion-order-dependent on `Set`/`Map` iteration that could vary between environments).

**Updated regression language, replacing the earlier byte-identical claim:** the personnel lines (SPV SCM, FRM SCM, Independent Sampler, PIC 3rd, Manpower {sampler}, Total Manpower) intentionally change from V2.2's PIC SCM/PIC AWK/Manpower AWK format to the shape above. All other approved output — Daily/WTD/MTD/YTD, buyer labels (`FPP HYNC`/`FPP SLNC`/`FPP ESG`), loading-area headings, and every calculation — must remain unchanged, and regression testing (Section 26) verifies the *non-personnel* sections byte-for-byte while verifying the *personnel* section against the target shape above, not against V2.2's old format.

**Unlicensed startup:**

## Section 30 — Final V2.3 Acceptance Summary

- Attempting `#/report` without Full Access always redirects to the Settings License card with the Full Access requirement message — never to Monitor, and never an alternate or ambiguous unlock explanation.
- Restricted Settings remains available in `MONITOR_ONLY` for License, Language, and Appearance only; Personnel Directory, Sync Status, and Pending Changes are not rendered into the page at all (not merely disabled).
- Indonesian and English UI selection works across the agreed scope (Section 12.3), with Monitor's legacy strings either translated or explicitly staged (Section 12.4).
- Dark, Light, and Auto appearance all work, exposed through Settings and unified across Monitor, Report, Settings, dialogs, and navigation — building on the theme behavior the application already had, not a newly invented one.
- Language and appearance persist locally, independent of license state and Report Reset.
- Automatic Week computes `weekNumber`/`weekYear`/`weekStart`/`weekEnd` from the active workbook's date using the ISO Monday–Sunday rule, renders read-only with no manual override, recalculates unconditionally on workbook replacement, and blocks progression on an invalid workbook date — it does not affect any buyer's calculations.
