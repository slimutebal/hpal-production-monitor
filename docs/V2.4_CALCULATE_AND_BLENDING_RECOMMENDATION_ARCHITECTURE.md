## Section 1 — Executive Summary

V2.4 adds one application page, **Calculate**, at route `#/calculate`, positioned between Monitor and Report in the bottom navigation:

```
Monitor | Calculate | Report | Settings
```

Phase 1 and Phase 2 are already implemented locally: the route/navigation/access shell exists, and Blend mode performs deterministic tonnage-weighted Ni calculation with a compact mobile input grid.

Calculate is **not** an engineering spreadsheet replacement. Its primary purpose is **field-operational blending support for HPAL ore feeding** — a mobile-first tool for a user standing near or coordinating the FPP hopper who needs fast answers to five questions:

1. What Ni will this blend produce?
2. How many DT of higher-grade material versus LGLO should enter the hopper?
3. What simple repeating hopper pattern should operators follow?
4. Which dome/pile should be **USE**d, **LIMIT**ed, or **STOP**ped for the current target?
5. If current material cannot reach target, what minimum Ni is required from an additional/new dome?

Calculate has two conceptual modes:

- **Blend** — given DT actually used, what Ni results?
- **Recommendation** — given active source inputs, physical reusable DT/fleet assigned to those sources, Contractor, and a Target Ni, what practical repeating hopper pattern should be followed, and how should the fleet be utilized?

The Recommendation engine is deterministic and tonnage-weighted. No AI/LLM is used anywhere in the calculation or recommendation path.

Recommendation has two distinct planning layers:

1. **Material/feed recommendation** — which source material contributes to the selected Hopper Pattern.
2. **Fleet utilization recommendation** — how many physical DT assigned to each source should remain in use, move within the same Contractor where practical, or be separated/placed on standby when all units cannot be productively used.

`Jumlah Unit` in Recommendation is now explicitly defined as **physical reusable DT/fleet assigned to the source**. It is not consumable load inventory: the same truck may return to the hopper repeatedly.

Contractor is also a first-class source attribute. Material from different Contractors may be blended in the same Hopper Pattern, while physical fleet reassignment is Contractor-aware: same-Contractor relocation is preferred; cross-Contractor relocation is secondary and requires coordination rather than being assumed freely available.

Calculate remains a `FULL_ACCESS`-only feature, gated using the existing route guard + action-boundary guard architecture. It reuses the application's existing ore-classification behavior, Dark/Light/Auto theme tokens, and id/en i18n infrastructure. It introduces no backend, no AI, no cloud sync, and no automatic coupling to Monitor or Report data.

The only remaining **blocking Gate A decision** before Recommendation implementation is the approved Operational Tolerance value and whether it is user-editable.

## Section 2 — Document Claims and Non-Claims

Stated explicitly:

- **V2.4 is partially implemented locally.** Phase 1 and Phase 2 exist on local `main` at the baseline recorded above. Recommendation, Hopper Pattern, fleet allocation, USE/LIMIT/STOP, and Planned Blend Recovery are not yet implemented.
- **`Jumlah Unit` in Recommendation is resolved.** It means the number of physical reusable DT currently assigned/active at that pile/source. It is not a finite load/rit inventory and is not depleted after one Hopper Pattern cycle.
- **Physical fleet count matters operationally.** Recommendation should maximize practical utilization of the entered fleet while protecting Target Ni/tolerance. If all units cannot be used without degrading the selected solution, excess units must be identified rather than forced into the blend.
- **Contractor is a required source attribute for Calculate's next input-model revision.** Contractor affects fleet relocation decisions, not the mathematical ability to blend material from different sources.
- **Material from different Contractors may be combined in one Hopper Pattern.** Physical DT, however, are not assumed freely transferable across Contractor boundaries.
- **Same-Contractor fleet relocation is preferred.** Cross-Contractor relocation is secondary/optional and must be labeled as requiring coordination if surfaced.
- **Material Action and Fleet Action are different outputs.** Material Action remains `USE` / `LIMIT` / `STOP`. Fleet Action concerns physical DT utilization such as `USE`, `MOVE`, or `SEPARATE / STANDBY`.
- **Hopper Pattern remains a feed/load instruction, not a physical fleet count.** A `1:2` pattern means one higher-grade load for every two LGLO loads in the repeated feed pattern; it does not mean only three physical trucks exist.
- **The exact recommendation-ranking numeric scoring weights are not pre-approved.** Ranking follows ordered deterministic priorities; implementation must not invent hidden arbitrary weights.
- **Operational tolerance is still unresolved and blocking.** Any `±0.010%` example in this document remains illustrative until the Owner explicitly approves a value and editability policy.
- **Ore classification remains derived, not user-entered.** Current local Phase 2 introduced `js/shared/ore-classification.js` for Calculate/shared Report use while preserving Monitor and the explicitly import-isolated ESG adapter behavior. Calculate must not introduce another independent threshold copy.
- **Recommendation is decision support, not autonomous control.** Nothing here authorizes automatic dispatch, hopper control, or equipment control.
- **Planned Blend Recovery is based on Calculate's own planned blend state**, not cumulative actual FPP production.
- **V2.4 remains undeployed.** Local implementation commits are intentionally not pushed until the Owner requests final push/deployment.

### 3.4 Pile, Dome, Source, and Contractor terminology

For Calculate, a **Pile/Dome/Source** is one physical source-material location entered as a row in the calculator. The document may use "Pile" in input-oriented wording and "Dome" in established operational wording, but they are not separate data entities.

**Contractor** is operational metadata attached to that source. It identifies the hauling Contractor responsible for the physical DT assigned to the source.

Contractor does **not** change ore chemistry or weighted-Ni math. It exists so later Recommendation logic can distinguish:

- material blending across Contractors, which is allowed; from
- physical fleet reassignment across Contractors, which must not be assumed freely available.

Final user-facing Pile-vs-Dome wording remains a non-blocking naming decision.

## Section 12 — User Input Model

The source model now contains **five** user-entered fields:

1. **Pile ID**
2. **Contractor**
3. **Ni (%)**
4. **Jumlah Unit**
5. **Tonase / Unit**

Derived fields:

- Ore Class — read-only, derived from Ni.
- Calculated Tonnage — read-only in Blend mode, `Jumlah Unit × Tonase / Unit`.

Contractor is operational metadata only in Blend mode and must not change weighted-Ni math.

### 12.1 Mobile input layout

The approved mobile pattern is a **compact table-like CSS Grid**, not large one-pile cards and not a horizontally scrolling desktop table.

Primary visible columns remain compact:

```
PILE | NI | DT | t/DT | action
```

Contractor is placed inside the PILE/source cell rather than adding a new wide column. Conceptually:

```
PILE             NI     DT    t/DT
───────────────────────────────────
L32_01          1.20    10     50   ×
SMA · MGLO                    500 t

L20_01          1.10    20     45   ×
TII · LGLO                    900 t

[blank trailing input row]
```

The grid must remain fully visible without horizontal scrolling at the primary 360–430 px viewport.

### 12.2 Trailing blank-row interaction

Blend input maintains exactly one completely blank trailing row.

- As soon as any of the five user fields is entered in the trailing row, that row becomes active and one new blank row is appended.
- The completely blank trailing row is excluded from validation and calculation.
- A partially completed active row is validated normally.
- Removing populated rows must preserve exactly one trailing blank row.
- Contractor participates in blank-row detection: a row is blank only when all five user fields are blank.

## Section 13 — Two Modes: Blend and Recommendation

Calculate presents two conceptual modes sharing the same source list and tonnage-weighted calculation core:

```
[ Blend ]   [ Recommendation ]
```

| | Blend | Recommendation |
| --- | --- | --- |
| Purpose | "I already know how many DT I used — what Ni did that produce?" | "Given current sources, physical fleet, Contractor boundaries, and Target Ni — what repeating hopper pattern should we operate?" |
| Jumlah Unit | DT/load count **actually used** in this blend | **Physical reusable DT/fleet assigned to the source** |
| Contractor | Metadata retained with the source; no effect on blend chemistry/math | Operational constraint for fleet relocation/utilization; does not prevent material from different Contractors being blended |
| Engine behavior | Direct weighted calculation, no search | Deterministic search/ranking for Target/tolerance plus fleet-utilization planning |
| Primary output | Final weighted Ni, totals, breakdown | Hopper Pattern, Unit/Tonnage Ratio, material actions, fleet utilization/actions, recovery when needed |

Blend semantics are implemented locally. Recommendation remains blocked only by the unresolved Operational Tolerance decision.

### 13.1 Approved Meaning of "Jumlah Unit" in Recommendation

`Jumlah Unit` in Recommendation is **physical reusable DT/fleet currently assigned/active at a pile/source**.

Example:

```
Pile A
Jumlah Unit = 5
```

means five physical DT are assigned to haul from that source.

It does **not** mean:

- only five total loads may ever be delivered;
- the source has a five-load consumable inventory;
- five DT are depleted after one Hopper Pattern cycle;
- only five hopper arrivals can occur from that source during the shift.

The same physical DT can repeatedly return to the hopper.

Recommendation may select an **active allocation** of `0 … entered physical DT` for each source when planning fleet utilization, but this range is a physical-fleet allocation range, not a consumable load inventory. Hopper Pattern load counts may repeat indefinitely within the operating period.

### 13.2 Fleet Utilization Objective

The engine should make practical use of as much of the entered active fleet as possible while protecting Target Ni/tolerance.

Conceptual priority:

1. Valid/physically representable recommendation.
2. Reach Target Ni / approved tolerance where possible.
3. Maximize practical utilization of entered physical DT.
4. Prefer a small/simple repeating Hopper Pattern.
5. Minimize unnecessary fleet separation or relocation.
6. Prefer same-Contractor relocation when relocation helps.
7. Minimize Ni deviation among otherwise comparable candidates.
8. Deterministic tie-break.

If all physical DT cannot be used without degrading the selected blend outside the accepted operating band, the engine must **not force them into the feed pattern**. Excess units must be surfaced as surplus/separate/standby or relocation candidates.

### 13.3 Contractor Boundary

Contractor affects physical fleet planning, not material compatibility.

**Allowed:**

- SMA material and TII material may both contribute to the same Hopper Pattern.
- The feed pattern may alternate loads from different Contractors.

**Preferred fleet relocation:**

- If one Contractor operates multiple sources, a surplus DT may be moved between those sources when useful.

**Cross-Contractor relocation:**

- Must not be assumed freely available.
- Must not be required to make the primary recommendation feasible by default.
- If surfaced as an alternative, it must be secondary and clearly indicate that coordination is required.

This distinction is mandatory throughout Recommendation logic and UI.

## Section 14 — Weighted Ni Calculation (Core Formula)

This formula underlies **every** calculation in Calculate — Blend, Recommendation candidate scoring, marginal impact, and recovery requirement all reduce to it.

```
Pile Tonnage_i  = Unit_i × TonnesPerUnit_i
Total Tonnage   = Σ Pile Tonnage_i

Weighted Ni     = Σ (Ni_i × Pile Tonnage_i)
                  ───────────────────────────
                          Total Tonnage
```

**Hard rules:**

- All recommendation and blend calculations MUST be tonnage-weighted.
- Never average pile Ni by pile count.
- Never average by DT count when tonnes/DT differ across piles.
- Total tonnage of zero means weighted Ni cannot be calculated — this is a validation failure (Section 29), not a divide-by-zero to silently guard into `0`.
- Retain full floating-point precision through every intermediate sum; round only at display time (Section 30). Never round a pile's contribution before summing across piles.

### Worked Example A — Weighted Blend

| Pile | Ni | Unit | Ton/Unit | Tonnage |
| --- | --- | --- | --- | --- |
| A | 1.30% | 10 | 50 | 500 t |
| B | 0.95% | 20 | 45 | 900 t |

```
Total Tonnage = 500 + 900 = 1400 t

Weighted Ni = (1.30 × 500) + (0.95 × 900)
              ────────────────────────────
                        1400

            = (650 + 855) / 1400
            = 1505 / 1400
            = 1.075%
```

## Section 16 — Target Ni, Tolerance, and Operational Simplicity

**Target Ni** is the operating quality objective the user enters for Recommendation mode — e.g. `1.120%`. It is conceptually distinct from any pile's sampled Ni:

- **Target Ni** = where the operation wants to go.
- **Pile Ni** = the current estimate of a source material's quality.

A sample result must never be treated as itself the target.

**Tolerance** is an acceptable ± band around Target Ni — e.g. `±0.010%` around `1.120%` gives an acceptable range of `1.110%–1.130%`. It exists because field operations should not be steered toward an unnecessarily complex hopper sequence for a mathematically tiny Ni improvement when a simpler pattern is already safely within target.

**Operational simplicity is a core V2.4 principle:** when candidate blends already fall inside the approved tolerance, simplicity outranks further mathematical optimization.

> Example: Candidate A at ratio `17:31` estimates `1.1201%`. Candidate B at ratio `1:2` estimates `1.118%`. If `1.118%` lies inside the approved target range, Recommendation should generally prefer the far simpler `1:2` pattern over the marginally closer `17:31` pattern.

**Operational Tolerance is the only remaining BLOCKING Gate A decision.** The Owner must approve its value and whether it is editable before Recommendation implementation begins. No tolerance may be silently hardcoded. Any specific value appearing in this document (for example `±0.010%`) remains illustrative only.

## Section 17 — Sampling / Recalculation Model

Field sampling is not a one-time event — pile/dome Ni values typically come from 2–3 samples per shift, and pile Ni is never assumed static for an entire shift.

**Recalculation trigger:** whenever a pile's Ni is updated (a new sample result is entered):

1. Ore class is recalculated from the authoritative classification rule (Section 11).
2. Blend calculation is recalculated.
3. Recommendation is recalculated.
4. Hopper Pattern may change.
5. Dome Action (USE/LIMIT/STOP) may change.
6. Recovery Requirement (Section 25) is recalculated if a recommendation was already in a target-not-achievable state.

```
10:00  S13_L02 Ni = 1.18   →  recommendation computed against this value
14:00  S13_L02 Ni = 1.25   →  user updates the value; recommendation recomputes
                              using 1.25, not 1.18, from this point on
```

**The recommendation always uses the latest user-entered value.** V2.4 core does not require server synchronization or sampling history (Decision 4, Section 41) — only the latest value per pile is the active calculation input. A future enhancement may preserve per-shift sample history, but that is out of scope here (Section 4.2).

## Section 18 — Recommendation Engine: Search Model and Priority Ranking

**Determinism is mandatory.** No AI/LLM is used in this engine.

Recommendation operates over two related but distinct concepts:

1. **Feed pattern candidate** — integer load counts/ratios that produce a tonnage-weighted Estimated Ni.
2. **Physical fleet allocation** — how many of the entered reusable DT assigned to each source are actively used to support the chosen operational recommendation.

The engine must never treat physical DT as consumable material inventory.

For candidate evaluation, calculate at minimum:

- source/load allocation underlying the repeating pattern;
- total load counts per pattern cycle;
- actual tonnes using each source's tonnes/DT;
- weighted Estimated Ni;
- absolute/signed deviation from Target Ni;
- tolerance status;
- ore-class totals;
- Higher Grade and LGLO load counts;
- simplified Unit Ratio;
- Tonnage Ratio;
- physical DT utilization by source/Contractor;
- surplus physical DT;
- feasible same-Contractor relocation options where relevant.

### 18.1 Default Recommendation Objective

The V2.4 core objective remains:

> **Find the smallest practical repeating Hopper Pattern that achieves Target Ni or falls inside the approved tolerance, while making practical use of the active physical fleet.**

Small patterns such as `1:1`, `1:2`, `2:3`, or `2:1` remain preferable to unnecessarily large patterns such as `17:31` once candidates are already within tolerance.

However, pattern simplicity must not be evaluated in isolation from fleet utilization. If two within-tolerance patterns are similarly simple, the pattern that productively uses more of the entered physical fleet should generally rank higher.

Conversely, fleet utilization must never be maximized by forcing surplus trucks to feed a source in a way that pushes the blend outside the approved operating band.

### 18.2 Deterministic Ranking Order

After Operational Tolerance is approved, implementation should use an ordered comparison rather than arbitrary hidden numeric weights:

1. Valid inputs and physically representable integer pattern.
2. Within Target Ni / approved tolerance where possible.
3. Greater practical utilization of the entered physical fleet.
4. Smaller/simpler repeating Hopper Pattern.
5. Less unnecessary fleet separation/relocation.
6. Same-Contractor relocation preferred over cross-Contractor relocation.
7. Smaller absolute Ni deviation among otherwise comparable candidates.
8. Less unnecessary source switching/complexity.
9. Deterministic normalized Pile ID / Contractor tie-break.

If no candidate can enter tolerance, Section 24's best-attainable path applies.

### 18.3 Feed Pattern vs Fleet Allocation

A repeating `1:2` Hopper Pattern does not mean exactly one high-grade truck and two LGLO trucks physically exist.

Example:

```
Pattern: 1 Higher Grade : 2 LGLO

Physical fleet:
Higher Grade source = 5 DT
LGLO source         = 8 DT
```

A practical allocation may be:

```
Higher Grade active = 4 DT
LGLO active         = 8 DT
Higher Grade surplus = 1 DT
```

while the hopper continues to follow the `1:2` load-arrival pattern repeatedly.

The surplus 1 DT must be reported separately or considered for same-Contractor relocation; it must not be forced into the pattern simply to claim 100% fleet utilization.

## Section 19 — Higher Grade Grouping, Unit Ratio, Tonnage Ratio

**Higher Grade grouping**, for hopper-pattern purposes only:

```
Higher Grade = HGLO + MGLO
Lower Grade  = LGLO
```

Primary operational ratio: `HGLO/MGLO : LGLO`.

> Example: HGLO = 2 DT, MGLO = 7 DT, LGLO = 18 DT → Higher Grade = 9 DT → primary unit ratio `9 : 18` → simplified `1 : 2`.

**Unit Ratio** is the GCD-simplified integer ratio of DT counts:

| Raw ratio | Simplified |
| --- | --- |
| 6 : 12 | 1 : 2 |
| 8 : 12 | 2 : 3 |
| 10 : 15 | 2 : 3 |
| 7 : 11 | 7 : 11 (already coprime) |

Meaning: `1 : 2` means, operationally, **1 DT of HGLO/MGLO for every 2 DT of LGLO**. This is the primary field-facing ratio (Section 20).

**Tonnage Ratio** is always calculated separately from the unit ratio — the two must never be conflated when tonnes/DT differ.

### Worked Example B — Unit Ratio vs Tonnage Ratio

```
Higher Grade: 1 DT × 50 t/DT = 50 t
LGLO:         2 DT × 45 t/DT = 90 t

Unit ratio:    1 : 2
Tonnage ratio: 50 / (50+90) : 90 / (50+90)  =  35.7% : 64.3%
```

Displaying `1:2` DT as if it were `33.3%:66.7%` tonnes would be incorrect here — the tonnage ratio must be computed and shown independently whenever tonnes/DT differ across the compared groups.

**Hard rule — tonnage still controls the math, regardless of how the Hopper Pattern is displayed.** Even though the Hopper Pattern is shown as a DT/load ratio (Section 20), Estimated Ni MUST be computed from Section 14's tonnage-weighted formula using each group's actual tonnes, never from the unit ratio directly. For the example above, Estimated Ni uses `50 t` and `90 t` — it must never be computed as `(1×NiHigher + 2×NiLGLO) / 3`, i.e. a simple average weighted by unit counts, unless tonnes/load are genuinely identical across every group being combined.

## Section 20 — Hopper Pattern and Hopper Sequence

**Hopper Pattern is the most visually prominent Recommendation result on mobile.** Estimated Ni remains verification information beneath the operational instruction.

```
┌──────────────────────────────┐
│       HOPPER PATTERN         │
│                              │
│           1 : 2              │
│                              │
│  HGLO/MGLO         LGLO      │
│     1 load          2 loads  │
│                              │
│           REPEAT             │
└──────────────────────────────┘
```

When multiple sources contribute, **Hopper Sequence** may show a concise actionable batching order, including Contractor identity where useful:

```
HOPPER SEQUENCE

1. SMA · Pile A     1 DT/load
2. TII · Pile C     2 DT/load
↻ REPEAT
```

This sequence is an operational feed instruction. It must not claim scientifically exact truck-by-truck mixing significance unless such a rule is separately approved.

### 20.1 Hopper Pattern Is a Feed Ratio, Not Physical Fleet Inventory

`1 : 2` means one Higher-Grade load for every two LGLO loads in the repeating hopper feed pattern.

It does **not** mean:

- exactly three physical trucks exist;
- only one Higher-Grade truck and two LGLO trucks are allocated;
- a physical truck is consumed after one cycle;
- the source can only deliver the number of loads displayed in one pattern cycle.

The same physical DT may return repeatedly.

Physical fleet utilization is shown separately. The engine may recommend that some of the entered DT remain active, move within the same Contractor, or be separated/placed on standby if they cannot all participate productively.

### 20.2 Tonnage Remains Authoritative

Hopper Pattern is displayed in integer load counts because that is operationally actionable, but Estimated Ni must always use actual tonnes/DT.

A `1:2` load ratio is not automatically a `33.3%:66.7%` tonnage ratio when tonnes/load differ.

## Section 21 — Maximum Complete Cycles (Future / Conditional — NOT V2.4 Core)

Maximum Complete Cycles is not part of V2.4 core.

The reason is now definitive: Recommendation-mode `Jumlah Unit` represents **physical reusable fleet**, not consumable loads. Therefore a formula such as:

```
min(
  floor(HigherGradeUnitsAvailable / HigherGradeUnitsPerCycle),
  floor(LGLOUnitsAvailable / LGLOUnitsPerCycle)
)
```

would be misleading if `UnitsAvailable` is merely the number of physical trucks, because the same trucks can return repeatedly.

A future cycle-exhaustion feature may only be introduced when a genuinely finite quantity exists, for example:

- planned loads/rit for a defined planning window;
- planned tonnage for a defined period;
- surveyed finite stockpile tonnage;
- an explicit time window combined with an approved throughput/cycle-time model.

Do not derive cycle exhaustion from physical truck count alone.

```
▸ Alternative 1
▸ Alternative 2
```

Alternatives must be visually secondary/collapsed by default — never an overwhelming optimizer result table. The exact count and selection of alternatives is an implementation detail governed by the ranking function of Section 18, not separately specified here.

## Section 23 — Material Action and Fleet Action

V2.4 distinguishes two different recommendation layers.

### 23.1 Material Action — USE / LIMIT / STOP

Material Action answers:

> **Should material from this source be fed under the current Target Ni conditions?**

The vocabulary remains:

- **USE**
- **LIMIT**
- **STOP**

These are dynamic recommendation states, never permanent source classifications.

**USE** — source has positive contribution in the primary recommendation and supports the selected solution.

**LIMIT** — source may still be used, but additional usage beyond the selected pattern would worsen distance from Target Ni or risk leaving tolerance.

**STOP** — conservative current-recommendation status, only when all hold:

1. the source has zero allocation in the selected recommendation;
2. adding one additional load moves the result farther from Target Ni; and
3. no feasible within-target/tolerance recommendation requires that source.

STOP means "do not feed this source in the next recommended pattern under current conditions," not a permanent blacklist.

### 23.2 Material Action Depends on the Primary Recommendation

Material Action is computed only after the primary recommendation is selected:

```
Inputs
  ↓
Candidate generation/ranking
  ↓
Primary Hopper Pattern
  ↓
Material Actions
  ├── USE
  ├── LIMIT
  └── STOP
```

This prevents contradictory output such as a source being marked STOP while the primary recommendation simultaneously requires it.

### 23.3 Material Action When Target Is Not Achievable

When tolerance cannot be achieved, Section 24's best-attainable candidate becomes the baseline.

- USE if the best-attainable candidate uses the source.
- LIMIT if additional usage worsens progress toward Target.
- STOP only if the source is unused in the best-attainable candidate and adding it makes the result worse.

### 23.4 Fleet Action — Separate from Material Action

Fleet Action answers:

> **What should happen to the physical DT currently assigned to this source?**

Conceptual fleet actions:

- **USE** — DT remains productively active at the source.
- **MOVE** — DT is a relocation candidate to another source.
- **SEPARATE / STANDBY** — DT should not be forced into the selected feed pattern; exact final label remains a UI wording choice.

Material Action and Fleet Action must not be conflated.

Example:

```
SMA · Pile A
Ni 1.24%

Material Action:
USE

Fleet:
4 DT USE
1 DT MOVE
```

### 23.5 Contractor-Aware Fleet Relocation

Relocation priority:

1. **Same Contractor** — preferred/allowed when another source operated by the same Contractor can use the surplus DT productively.
2. **Cross Contractor** — not assumed freely available. May be shown only as a secondary coordination-required option if the Owner later wants it surfaced.
3. If no appropriate relocation exists, surplus DT remains **SEPARATE / STANDBY**.

Different-Contractor material may still feed the same Hopper Pattern. Contractor restricts physical fleet reassignment, not blend chemistry.

### 23.6 Pile Impact (Marginal Contribution)

For explanation/detail:

```
New Ni = (CurrentNi × CurrentTonnage + PileNi × TonnesPerDT)
         ─────────────────────────────────────────────────────
                    CurrentTonnage + TonnesPerDT

Impact = New Ni − Current Ni
```

Impact describes direction/magnitude of adding one load. It must never by itself determine USE/LIMIT/STOP; the direction relative to Target Ni still governs.

## Section 24 — Target Not Achievable Detection

The engine must explicitly detect when Target Ni (± tolerance) cannot be reached given the currently entered sources, tonnage/load values, and approved physical-fleet/Contractor constraints, and must never present a misleading "best recommendation" as though the target were achievable.

```
TARGET NOT ACHIEVABLE
with current available material

Best attainable Ni:  1.087%
Target:               1.120%
Gap:                 -0.033%
```

The best attainable blend is still shown, but labeled explicitly as the best attainable result, not as a successful recommendation. Dome Actions (USE/LIMIT/STOP) in this state follow Section 23.3, not Section 23.1's within-target definitions — they are evaluated relative to the best attainable candidate, never issued as if the unreachable target had been met.

## Section 25 — Planned Blend Recovery (New Dome / Recovery Requirement)

When available material cannot reach Target Ni, calculate the **minimum Ni** an additional/new source must have to correct the blend, for an arbitrary added tonnage.

### 25.1 V2.4 Core Baseline — Explicit and Non-Ambiguous

`CurrentNi` and `CurrentTonnage` in the formula below are ambiguous unless the baseline is pinned down. **For V2.4 core, Recovery Requirement is calculated against the CURRENT PLANNED BLEND STATE already entered inside Calculate — nothing else:**

- It is **not** cumulative actual FPP production.
- It is **not** automatically taken from Monitor.
- It is **not** automatically taken from Report.
- It is **not** a lab-feed cumulative result.

Conceptually:

```
Current planned blend (Calculate's own piles/inputs)
        +
proposed additional/new dome
        ↓
   Target Ni
```

`CurrentNi`/`CurrentTonnage` are the weighted Ni and total tonnage (Section 14) of whatever blend is currently defined inside Calculate — e.g. the best blend achievable from the currently entered piles, or the primary Recommendation's candidate. If a Recovery calculation is requested and no clearly-defined finite baseline blend exists yet inside Calculate (e.g. no piles entered, or Recommendation has not been run), the UI must ask the user for or derive an explicit, clearly-defined finite baseline rather than inventing one silently.

**Terminology requirement:** label this feature "**Planned Blend Recovery**" in UI copy and documentation, never "Actual Shift Recovery" or similar wording that implies correcting the whole shift or whole FPP production — V2.4 core does not know real cumulative feed Ni, authoritative tonnage already fed, or remaining planned production tonnage (Section 28), so it must never display a correction as if it were correcting actual cumulative production.

```
AddedTonnage = AddedDT × TonnesPerDT

RequiredNewNi = TargetNi × (CurrentTonnage + AddedTonnage) − CurrentNi × CurrentTonnage
                ───────────────────────────────────────────────────────────────────────
                                        AddedTonnage
```

### Worked Example E — Planned Blend Recovery Requirement

```
Current planned blend (inside Calculate):  1.085%,  1000 t
Target:                                     1.120%
Candidate correction: 5 DT × 50 t/DT = 250 t

RequiredNewNi = (1.120 × 1250) − (1.085 × 1000)
                ───────────────────────────────
                             250

              = (1400 − 1085) / 250
              = 315 / 250
              = 1.260%
```

```
PLANNED BLEND RECOVERY — NEED NEW DOME
For 5 DT × 50 t/DT
Minimum Ni ≥ 1.260%
```

**Recovery Options** — because the required Ni depends on how much new tonnage is added, the UI should be able to show several scenarios:

```
NEW DOME REQUIREMENT

 5 DT   ≥ 1.55%
10 DT   ≥ 1.35%
15 DT   ≥ 1.28%
```

The specific DT presets shown (5/10/15 above) are illustrative only — **do not hardcode these as business constants in the architecture.** They are UI presets to be finalized during implementation (Section 41, Decision 3). The underlying `calculateRequiredNewDomeNi(...)` function must accept arbitrary Added DT and Tonnes/DT — never a fixed preset list baked into the calculation itself.

## Section 27 — Sampling-Driven Field Workflow

This workflow is central to Recommendation.

**Start of shift / planning update:**

1. User sets Target Ni.
2. User enters active Pile IDs.
3. User enters Contractor for each source.
4. User enters latest sampled Ni per source.
5. User enters physical reusable DT currently assigned to each source.
6. User enters tonnes/DT per source.
7. Calculate Recommendation.
8. Review Hopper Pattern.
9. Review fleet utilization, surplus DT, and any same-Contractor move candidates.
10. Field team executes the approved operational pattern.

**New sample arrives (commonly multiple times per shift):**

11. Update the affected source's Ni.
12. Recalculate.
13. Review the possibly changed Hopper Pattern.
14. Review updated Material Actions.
15. Review updated Fleet Actions/utilization.
16. Continue operation.

**If target becomes impossible:**

17. Show `TARGET NOT ACHIEVABLE`.
18. Show the best-attainable recommendation.
19. Show Planned Blend Recovery minimum-Ni requirement when applicable.

The latest entered Ni remains authoritative for current calculation. Sampling history remains future scope.

## Section 28 — Closed-Loop Feed Correction (Future / Optional, V2.4.x)

Earlier design discussion considered a more advanced mode using actual cumulative FPP feed Ni, tonnage already fed, and remaining planned tonnage, to compute a correction target for the *remaining* material:

```
Required Remaining Ni = (Target × Planned Total Tonnes) − (Cumulative Ni × Tonnes Already Fed)
                         ────────────────────────────────────────────────────────────────────────
                                                  Remaining Tonnes
```

This is valuable but is explicitly **not** mandatory V2.4 core, and must not be implemented as part of the phases in Section 40 unless separately approved. The reason: the core V2.4 requirement has a clear definition for pile-sampling updates (Section 17), but "cumulative feed-sample" and "tonnage already fed" have no defined authoritative data source in the current application, and implementation must not infer that semantics on its own. This is documented here as **Future / V2.4.x Closed-Loop Enhancement**, pending Owner definition of those data sources (Section 41, Decision 5).

## Section 31 — Performance, Search Space, and Determinism

Recommendation must remain deterministic and responsive on a mobile device.

Because `Jumlah Unit` is physical reusable fleet, the engine must **not** enumerate consumable load inventories as though each source can only be used N times total.

A practical deterministic architecture may separate:

1. **Small repeating Hopper Pattern search** — enumerate compact integer load ratios/patterns first and evaluate them by actual tonnes/load and Target/tolerance.
2. **Fleet utilization/allocation** — for each viable pattern, determine how many of the entered physical DT can productively remain assigned, which surplus units exist, and whether same-Contractor relocation improves utilization.
3. **Ranking** — apply Section 18's ordered criteria.

Physical fleet allocation per source may be bounded by `0 … entered physical DT`, but this is an allocation bound, not a load-consumption bound.

Acceptable deterministic techniques include bounded small-ratio enumeration, branch-and-bound, grouped class search followed by source allocation, and deterministic pruning. No random search and no AI/LLM optimizer.

Correctness tests must assert outputs/constraints rather than internal algorithm details so the implementation strategy can evolve without changing the product contract.

## Section 42 — V2.4 Acceptance Criteria / Definition of Done

**Navigation/access**

- `FULL_ACCESS`: `Monitor | Calculate | Report | Settings`.
- `MONITOR_ONLY`: `Monitor | Settings`.
- Calculate remains route-guarded and action-boundary-guarded.

**Source input**

- Source model includes Pile ID, Contractor, Ni, Jumlah Unit, and Tonase/Unit.
- Ore Class is derived.
- Compact mobile grid fits 360–430 px without horizontal scrolling.
- Exactly one trailing blank row is maintained.

**Blend**

- Deterministic, tonnage-weighted.
- Contractor metadata never changes weighted-Ni arithmetic.
- Existing Phase 2 Blend behavior remains regression-protected.

**Recommendation**

- Target Ni remains user-defined.
- Operational Tolerance follows the Owner-approved Gate A decision.
- Hopper Pattern is a small practical repeating load/feed ratio.
- Actual tonnes/DT control all Ni math.
- Physical DT are reusable fleet, never consumable load inventory.
- Recommendation reports physical fleet utilization separately from Hopper Pattern.
- If all physical DT cannot be used productively, surplus units are explicitly identified rather than forced into the blend.
- Same-Contractor relocation is preferred when useful.
- Cross-Contractor relocation is not silently assumed.
- Material from different Contractors may still feed the same Hopper Pattern.

**Actions**

- Material Action = `USE` / `LIMIT` / `STOP`.
- Fleet Action is separate and may express `USE`, `MOVE`, `SEPARATE / STANDBY`.
- Material and Fleet Actions cannot contradict the selected primary recommendation.
- Target-not-achievable uses the best-attainable baseline.

**Sampling**

- Latest entered source Ni can be updated and Recommendation recomputes from that latest value.

**Recovery**

- Planned Blend Recovery uses Calculate's own planned blend baseline and never implies correction of cumulative actual FPP production.

**Regression**

- Monitor, Report, Settings, Personnel Directory, License, Language/Appearance, and existing V2.3 behavior remain regression-protected.
- V2.4 is not pushed/deployed until Owner approval after final regression.
