## Section 1 — Executive Summary

V2.4 adds one new application page, **Calculate**, at route `#/calculate`, positioned between Monitor and Report in the bottom navigation:

```
Monitor | Calculate | Report | Settings
```

Calculate is **not** an engineering spreadsheet replacement. Its primary purpose is **field-operational blending support for HPAL ore feeding** — a mobile-first tool for a user standing near or coordinating the FPP hopper who needs fast answers to five questions:

1. What Ni will this blend produce?
2. How many DT of higher-grade material versus LGLO should enter the hopper?
3. What simple repeating hopper pattern should operators follow?
4. Which dome/pile should be **USE**d, **LIMIT**ed, or **STOP**ped for the current target?
5. If current material cannot reach target, what minimum Ni is required from an additional/new dome?

Calculate has two modes — **Blend** (given DT actually used, what Ni results) and **Recommendation** (given available DT and a Target Ni, what hopper pattern should be followed) — built on one shared, deterministic, tonnage-weighted calculation core. No AI/LLM is used anywhere in the recommendation engine; it is pure arithmetic and integer search.

Calculate is a `FULL_ACCESS`-only feature, gated the same way Report is gated today (route guard + action-boundary guard, per V2.3 Section 10's pattern). It reuses the application's existing ore-classification thresholds rather than defining its own, reuses the existing Dark/Light/Auto theme tokens, and uses the existing id/en i18n infrastructure. It introduces no backend, no AI, no cloud sync, and no automatic coupling to Monitor or Report data.

## Section 2 — Document Claims and Non-Claims

Stated explicitly, following the precedent set by V2.3 Section 2:

- **Nothing in this document is implemented.** No `#/calculate` route, no `js/pages/calculate/**` module, no navigation change, and no i18n key listed below exists in the repository today. This document is the specification a later implementation task must follow — it does not itself change `index.html`, `router.js`, `bottom-navigation.js`, `service-worker.js`, or `README.md`.
- **What "Jumlah Unit" means in Recommendation mode is NOT decided here, and this document no longer assumes an answer.** An earlier draft of this document assumed "Jumlah Unit = Available DT" and treated it as consumable inventory (`0 … Available DT`). That assumption was **not approved** and has been removed (Section 13.1). Whether Jumlah Unit means physically reusable trucks/fleet or a finite planned load/rit count is a **blocking open decision** (Section 41, Decision 1) — Recommendation-engine implementation must not begin until it is resolved (Gate A, Section 40).
- **The exact recommendation-ranking scoring weights are not decided here.** Section 18 documents the *conceptual* priority order (feasibility → tolerance → simplicity → deviation → complexity) and explicitly defers the numeric weights to implementation-time testing against real operational data, gated on both blocking decisions (Section 41, Decisions 1 and 2).
- **The operational tolerance value is not decided here.** Section 16 documents the *concept* of tolerance and explicitly marks the default value as a **blocking** open Owner decision (Section 41, Decision 2) — it must not be silently hardcoded during implementation. Illustrative values such as `±0.010%` appearing anywhere in this document are examples only, never an approved default.
- **The current ore-classification thresholds are recorded as found (`> 1.4` → HGLO, `< 1.2` → LGLO, else → MGLO), and this document reuses them — it does not itself introduce or change any threshold.** These already exist in three independent copies in the current codebase (Section 3.2); V2.4 must not add a fourth.
- **"Pile" and "Dome" are documented as the same source-material entity for this feature** (Section 3.4, Section 6) — final UI wording is still an open Owner decision (Section 41, Decision 6).
- **The Hopper Pattern is a load/feed instruction, never an implied physical fleet count.** Section 20.1 states explicitly that a `1:2` pattern does not mean "exactly three trucks exist" or that trucks are consumed after one cycle — the same physical trucks may participate repeatedly.
- **Recommendation is decision support, not autonomous control.** Section 39 states this explicitly; nothing in this document describes or implies automatic hopper/dispatch control.
- **Recovery Requirement (Section 25) is calculated against Calculate's own current planned blend, not against actual cumulative FPP production.** This document does not claim to know real cumulative feed Ni or tonnage already fed — see Section 25's baseline clarification and Section 28.
- **V2.3 remains the currently implemented and deployed baseline.** V2.4 is the planned target version this document describes.

## Section 3 — Repository Baseline Findings

### 3.1 Current routing and navigation architecture (found)

`js/router.js` is a minimal hash router:

```js
const DEFAULT_ROUTE = 'monitor';
const ROUTE_PATTERN = /^#\/(monitor|report|settings)$/;
```

- Exactly three routes exist today: `monitor`, `report`, `settings`. Anything else (empty hash, unknown hash, a route with a trailing segment) falls back to `monitor` via `applyRoute()`'s redirect-and-reapply logic.
- `registerRouteGuard(route, guardFn, onDeny)` (added in V2.3 Phase 8) lets `app.js` gate a route: `guardFn(route)` returning `false` causes `onDeny(route)` to run instead of activating the page, and the router never falls through to render the guarded page.
- `js/app.js` registers exactly one guard today, for `report`: allowed only when `hasFullAccess()` is `true`; on deny it calls `navigateTo('settings')` then `requestFullAccessAttention('route-report')` — never redirects back to `#/report`, never to `#/monitor`.
- `js/components/bottom-navigation.js` renders from a `NAV_ITEMS` array, in array order: `monitor`, `report` (flagged `fullAccessOnly: true`), `settings`. The render step is `NAV_ITEMS.filter((item) => !item.fullAccessOnly || fullAccess)` — under `MONITOR_ONLY` the Report item is not rendered at all (not merely disabled), which is exactly the pattern Section 9 below reuses for Calculate.
- `index.html` declares the page containers the router toggles between: `<section id="page-monitor">`, `<section id="page-report">`, `<section id="page-settings">`, all children of `<main id="app-pages">`. Report and Settings are empty shells populated at runtime by `initReportPage()`/`initSettingsPage()` (called from `js/app.js`); Monitor is inline markup/script already present in `index.html`.

**Conclusion for V2.4:** the routing architecture already has a proven guard mechanism built for exactly this kind of licensed-page addition. Calculate should extend `ROUTE_PATTERN`, add a `page-calculate` container, add a `calculate` entry to `NAV_ITEMS`, and register a guard — following the `report` precedent, not inventing a new mechanism.

### 3.2 Current ore-classification source(s) found — **not currently a single source of truth**

A repository-wide search (`git grep -n "LGLO\|MGLO\|HGLO\|classifyOre\|oreClass"`) found the classification rule implemented **independently, three times**, all with the same thresholds:

| # | Location | Function | Rule |
| --- | --- | --- | --- |
| 1 | `index.html:1198-1203` | `classifyOre(grade)` | `grade > 1.4 → HGLO`; `grade < 1.2 → LGLO`; else `MGLO` — used by Monitor's own class/dome breakdown and charts. |
| 2 | `js/pages/report/profiles/shared-report-profile.js:206-208` | `classifyOreClass(grade)` | Identical rule. Its own comment states it mirrors "Monitor's own identical `classifyOre()` in `index.html`" — an intentional duplication, not a shared import. |
| 3 | `js/pages/report/profiles/adapters/esg-adapter-utils.js:148-155` | `classifyEsgOreClass(grade)` (called `classifyEsgOreClass` internally, feeding `oreClass` on ESG adapter output) | Identical rule again, with its own comment warning it "must stay in sync if ever revisited." |

All three agree on the same boundary behavior:

```
grade < 1.20            → LGLO
1.20 <= grade <= 1.40    → MGLO   (">= 1.20" via "not < 1.20"; "<= 1.40" via "not > 1.40")
grade > 1.40             → HGLO
```

**This is the important finding for V2.4:** the codebase does **not** currently have one shared classification helper — it has three independently maintained copies that happen to agree today. V2.4 must not add a **fourth** independent copy. Section 11 requires implementation to either import one of these three, or (preferably) extract a single shared pure `classifyOre(ni)` helper that all four call sites (Monitor, `shared-report-profile.js`, `esg-adapter-utils.js`, and the new Calculate module) use — a decision for the implementation phase, made against the actual code at that time, not pre-decided here. The boundary values recorded above (`1.199…` → LGLO, `1.20` → MGLO, `1.40` → MGLO, `>1.40` → HGLO) apply **only if they still match production code when implementation begins** — this document is not the authority on the threshold itself, current code is.

### 3.3 Current license/access behavior (found)

`js/services/license-service.js` implements a local, offline `MONITOR_ONLY` / `FULL_ACCESS` gate (V2.3 Phase 8 — see that document's Sections 6–11 for full detail; summarized here as found):

- `ACCESS_TIERS = { MONITOR_ONLY, FULL_ACCESS }`; `hasFullAccess()` returns a boolean derived fresh from a validated local storage record on every check — never a cached flag trusted blindly.
- `FULL_ACCESS` is granted by a locally-verified PBKDF2-HMAC-SHA-256 proof against one Owner-held access key; there is no per-feature license.
- `requestFullAccessAttention(context)` / `subscribeFullAccessAttention(callback)` is a separate pub/sub Settings subscribes to, used by both the router guard (`app.js`) and Report's own action-boundary guard (`report-page.js`'s `requireFullAccessForReportAction()`) to ask Settings to open/focus the License card after a deny-and-redirect.
- Report enforces access at **two independent layers**: the route guard (`app.js`, blocks reaching `#/report` at all) and an action-boundary guard inside `report-page.js` (blocks a direct programmatic call that bypasses the router). Both redirect to `#/settings` and call `requestFullAccessAttention()`.
- The bottom nav hides the Report item entirely under `MONITOR_ONLY` (Section 3.1) — but this is documented in the code itself as **UX only, never the actual security boundary**.

**Conclusion for V2.4:** Calculate must reuse this exact two-layer pattern (route guard + action-boundary guard), not invent a new one, and must not introduce any new license tier.

### 3.4 "Pile" vs "Dome" terminology (found)

The current codebase and README consistently use **"dome"** for the source-material entity: `DOME-12`, `DOME-03` (README ΔNI attribution examples), `domesByClass` (`index.html:1235`), `d.dome` (`shared-report-profile.js`, `esg-profile.js`, `report-page.js`), and collapsible "dome sub-rows" in Report's Man Power card. The word **"pile"** does not appear anywhere in the current codebase or README — it is a term introduced by this V2.4 specification (and by the field-operations vocabulary it is based on) to describe a single blend-calculator input row.

**Conclusion for V2.4:** for this feature, "Pile" and "Dome" refer to the **same underlying source-material entity** — a discrete stockpile the operator samples and feeds from. Section 6 fixes "Pile ID" as the input-entity label (matching this document's terminology and not conflicting with any existing repo naming, since none exists), while recommendation/action wording may still say "dome" operationally (e.g. "Dome Action: STOP") to match the field vocabulary the README and Monitor's own UI already use. Implementation must **not** silently invent two separate data entities (a "Pile" record and a separate "Dome" record) for one feature — there is exactly one entity, with two names in different contexts. Final UI wording is Decision 6 in Section 41.

## Section 6 — Terminology

| Term | Meaning |
| --- | --- |
| Pile ID | The input-entity label for one blend-calculator row (Section 3.4) — the same physical source as a "dome" elsewhere in the app. |
| Ni (%) | Nickel grade of a pile's sampled material. |
| Jumlah Unit / DT | Dump-truck unit count. In Blend mode this unambiguously means DT *actually used* (Section 15). **In Recommendation mode, what this number represents is not yet defined** — physically reusable trucks/fleet, or a finite planned load/rit count are both possible readings, with materially different math. This is a blocking open decision — see Section 13.1. |
| Tonase per Unit | Tonnes per DT for a given pile (varies by pile — must never be assumed uniform across piles). |
| Calculated Tonnage | `Jumlah Unit × Tonase per Unit` for one pile. |
| LGLO / MGLO / HGLO | Ore classes, derived automatically from Ni via the single classification source (Section 11) — never user-entered. |
| Higher Grade | `HGLO + MGLO` combined, for hopper-pattern purposes (Section 19). |
| Lower Grade | `LGLO` alone. |
| Target Ni | The operating quality objective the field team wants the blend to achieve — entered by the user, never inferred from a sample (Section 16). |
| Estimated Ni | The tonnage-weighted Ni a candidate or actual blend is calculated to produce. |
| Deviation | `Estimated Ni − Target Ni` (signed or absolute, per display context — Section 16). |
| Tolerance | An acceptable ± band around Target Ni, inside which operational simplicity is preferred over further Ni optimization (Section 16). |
| Hopper Pattern | The primary field-facing output: a simplified Higher-Grade : LGLO unit ratio to repeat at the hopper (Section 20). |
| Unit Ratio | The GCD-simplified integer ratio of DT counts between two groups (Section 19). |
| Tonnage Ratio | The percentage split of actual tonnes between two groups — never assumed equal to the unit ratio when tonnes/DT differ (Section 19). |
| Available DT *(provisional term)* | Used loosely throughout early drafts of this document to mean "the Jumlah Unit entered for a pile in Recommendation mode." **Its exact operational meaning — physically reusable fleet capacity vs. a finite planned load count — is unresolved (Section 13.1)**; wherever it still appears below it means only "the number entered for that pile," not a confirmed consumable-inventory bound. |
| Recommendation | The engine's best (and optionally alternative) candidate blend composition for a given Target Ni, expressed as a repeating Hopper Pattern (Section 18.1) rather than a one-shot inventory allocation. |
| Dome Action | A dynamic per-pile operational suggestion — `USE` / `LIMIT` / `STOP` — computed from the primary recommended Hopper Pattern against the current target and blend state, never a fixed property of a pile and never computed independently of that primary recommendation (Section 23). |
| Recovery Requirement | The minimum Ni an additional/new source must have to bring Calculate's own current **planned** blend (not actual cumulative FPP production) back to Target Ni — see "Planned Blend Recovery," Section 25. |

## Section 13 — Two Modes: Blend and Recommendation

Calculate presents two tabs sharing one input list and one calculation core:

```
[ Blend ]   [ Recommendation ]
```

| | Blend | Recommendation |
| --- | --- | --- |
| Purpose | "I already know how many DT I used — what Ni did that produce?" | "I have a Target Ni — what repeating hopper pattern gets me there?" |
| "Jumlah Unit" means | DT **actually used** — unambiguous | **Not yet defined — BLOCKING, see Section 13.1** |
| Engine behavior | Direct weighted calculation, no search | Deterministic search for the smallest practical repeating Hopper Pattern (Section 18.1); the exact search boundary per pile cannot be finalized until Section 13.1 is resolved |
| Primary output | Final weighted Ni, totals, breakdown | Hopper Pattern, Unit/Tonnage Ratio, Dome Actions, Recovery (if needed) |

Blend mode's semantics are fully resolved and safe to implement ahead of Recommendation (Section 40, Phase 2). Recommendation mode's engine is **not** safe to implement until Section 13.1's blocking question is answered by the Owner (Section 40, Gate A).

### 13.1 Meaning of "Jumlah Unit" in Recommendation — BLOCKING OPEN DECISION

An earlier draft of this architecture assumed, without qualification, that "Jumlah Unit" in Recommendation mode means **Available DT**, treated as consumable material inventory: the engine searched `0 … Available DT` per pile, a pile's availability was implicitly "used up" by a recommendation, and maximum achievable cycles were derived directly from it. **That assumption was never approved and is withdrawn.** The actual field meaning of "Jumlah Unit" in Recommendation mode is still unresolved, and the two candidate interpretations are fundamentally different calculations, not a wording nuance:

**Interpretation A — physical DT/fleet capacity.** "Jumlah Unit" counts the number of physical dump trucks currently assigned to haul from a pile/dome.

- The same truck can return to the hopper repeatedly within a shift.
- An entry of `5` does **not** mean only 5 loads can ever be delivered from that pile — it is a reusable operational resource, not a depletable material quantity.
- Under this interpretation, there is no natural "exhaustion" of a pile from a single recommendation, and any notion of "remaining DT after using N" is meaningless without a separately defined time window or planned load count.

**Interpretation B — planned loads/rit within a defined recommendation window.** "Jumlah Unit" counts a finite number of planned loads (rit) the pile is expected to contribute within some explicit window (e.g. a shift or a planning horizon).

- An entry of `5` legitimately means five loads, and can be consumed/allocated by a recommendation the way the withdrawn draft assumed.
- This interpretation requires the window itself (shift, hours, planned tonnage target) to be defined somewhere in the UI — it does not exist implicitly just because a number was typed into "Jumlah Unit."

**Requirement:** implementation of the Recommendation search boundary (what upper bound, if any, constrains each pile's contribution to a candidate) **MUST NOT begin until the Owner confirms which interpretation applies** — see Section 41, Decision 1, and Gate A in Section 40. Until then:

- This document does **not** state that Recommendation search is bounded by `0 … Available DT`.
- This document does **not** treat a pile's entered Jumlah Unit as consumable inventory.
- This document does **not** claim a pile's availability is depleted after one recommendation.
- This document does **not** derive "maximum achievable cycles" from Jumlah Unit alone (see Section 21, which is deferred out of V2.4 core specifically because of this).

## Section 14 — Weighted Ni Calculation (Core Formula)

This formula underlies **every** calculation in Calculate — Blend, Recommendation candidate scoring, marginal impact, and recovery requirement all reduce to it.

```
Pile Tonnage_i  = Unit_i × TonnesPerUnit_i
Total Tonnage   = Σ Pile Tonnage_i

Weighted Ni     = Σ (Ni_i × Pile Tonnage_i)
                  ───────────────────────────
                          Total Tonnage
```

**Hard rules:**

- All recommendation and blend calculations MUST be tonnage-weighted.
- Never average pile Ni by pile count.
- Never average by DT count when tonnes/DT differ across piles.
- Total tonnage of zero means weighted Ni cannot be calculated — this is a validation failure (Section 29), not a divide-by-zero to silently guard into `0`.
- Retain full floating-point precision through every intermediate sum; round only at display time (Section 30). Never round a pile's contribution before summing across piles.

### Worked Example A — Weighted Blend

| Pile | Ni | Unit | Ton/Unit | Tonnage |
| --- | --- | --- | --- | --- |
| A | 1.30% | 10 | 50 | 500 t |
| B | 0.95% | 20 | 45 | 900 t |

```
Total Tonnage = 500 + 900 = 1400 t

Weighted Ni = (1.30 × 500) + (0.95 × 900)
              ────────────────────────────
                        1400

            = (650 + 855) / 1400
            = 1505 / 1400
            = 1.075%
```

## Section 15 — Blend Mode Specification

**Input:** per pile — Pile ID, Ni, DT used, tonnes/DT.

**Output (minimum):**

- Total DT
- Total Tonnage
- Weighted / Final Ni
- Pile breakdown (per-pile tonnage contribution, Ni contribution, % of total tonnage)
- Ore-class breakdown (tonnage/DT per LGLO/MGLO/HGLO)
- Higher Grade total (HGLO + MGLO)
- LGLO total

Secondary engineering detail (per-pile tonnage/Ni contribution, % of total) is useful but must be visually subordinate on mobile (Section 32) — Blend mode still leads with the final weighted Ni.

Blend mode performs **no search** — it is a direct application of Section 14's formula to exactly the DT values entered.

## Section 16 — Target Ni, Tolerance, and Operational Simplicity

**Target Ni** is the operating quality objective the user enters for Recommendation mode — e.g. `1.120%`. It is conceptually distinct from any pile's sampled Ni:

- **Target Ni** = where the operation wants to go.
- **Pile Ni** = the current estimate of a source material's quality.

A sample result must never be treated as itself the target.

**Tolerance** is an acceptable ± band around Target Ni — e.g. `±0.010%` around `1.120%` gives an acceptable range of `1.110%–1.130%`. It exists because field operations should not be steered toward an unnecessarily complex hopper sequence for a mathematically tiny Ni improvement when a simpler pattern is already safely within target.

**Operational simplicity is a core V2.4 principle:** when candidate blends already fall inside the approved tolerance, simplicity outranks further mathematical optimization.

> Example: Candidate A at ratio `17:31` estimates `1.1201%`. Candidate B at ratio `1:2` estimates `1.118%`. If `1.118%` lies inside the approved target range, Recommendation should generally prefer the far simpler `1:2` pattern over the marginally closer `17:31` pattern.

**Whether tolerance is user-editable in the initial UI, and what its default value is, is a BLOCKING open Owner decision (Section 41, Decision 2).** No operational tolerance may be hardcoded until Owner approval — this remains blocking for final Recommendation ranking behavior (Section 18), not merely a nice-to-have default. Any specific value appearing anywhere in this document (e.g. `±0.010%` above) is illustrative only and must never be read as an approved default.

## Section 17 — Sampling / Recalculation Model

Field sampling is not a one-time event — pile/dome Ni values typically come from 2–3 samples per shift, and pile Ni is never assumed static for an entire shift.

**Recalculation trigger:** whenever a pile's Ni is updated (a new sample result is entered):

1. Ore class is recalculated from the authoritative classification rule (Section 11).
2. Blend calculation is recalculated.
3. Recommendation is recalculated.
4. Hopper Pattern may change.
5. Dome Action (USE/LIMIT/STOP) may change.
6. Recovery Requirement (Section 25) is recalculated if a recommendation was already in a target-not-achievable state.

```
10:00  S13_L02 Ni = 1.18   →  recommendation computed against this value
14:00  S13_L02 Ni = 1.25   →  user updates the value; recommendation recomputes
                              using 1.25, not 1.18, from this point on
```

**The recommendation always uses the latest user-entered value.** V2.4 core does not require server synchronization or sampling history (Decision 4, Section 41) — only the latest value per pile is the active calculation input. A future enhancement may preserve per-shift sample history, but that is out of scope here (Section 4.2).

## Section 18 — Recommendation Engine: Search Model and Priority Ranking

**Determinism is mandatory.** No AI/LLM anywhere in this engine — it is a deterministic search over integer, physically representable Hopper Patterns.

**Search space:** the engine searches over candidate integer Hopper Patterns (Higher-Grade : LGLO unit ratios and the pile allocation behind them, Section 19), not over an assumed `0 … Available DT` consumable range per pile — Section 13.1 has not yet established what upper bound, if any, legitimately constrains a pile's contribution. Until that blocking decision is resolved, "the search space" is deliberately described here only in terms of what is safe to state today: for every candidate, calculate

- DT/load count per pile
- Total DT/load count
- Total tonnes
- Weighted estimated Ni (Section 14)
- Absolute deviation from Target Ni
- Ore-class totals
- Higher Grade units
- LGLO units
- Unit ratio (Section 19)
- Tonnage ratio (Section 19)

Whatever finite constraint the Owner confirms in Section 13.1 (physical fleet capacity used as a soft/contextual limit, or a hard finite planned-load cap) is what "feasible" means in the ranking criteria below — this document intentionally does not pre-decide it.

**Core safety requirement:** ranking and reporting are based on actual `DT × tonnes/DT`, never on DT ratio alone — a 1:2 DT ratio between piles with different tonnes/DT is not a 1:2 tonnage ratio (Section 19 makes this explicit).

**Conceptual candidate ranking**, reflecting the smallest-repeating-pattern operational focus (Section 18.1) rather than inventory exhaustion (exact scoring weights are explicitly **not** decided here — Section 41, Decisions 1 and 2 — and must be defined and tested against real operational scenarios before implementation, never invented ad hoc by the implementer):

1. Valid inputs / a physically representable integer Hopper Pattern.
2. Respects whatever operational constraint the Owner confirms in Section 13.1 (feasibility is not assumed to mean "never exceeds Available DT" until that decision closes).
3. Reaches Target Ni / the approved tolerance where possible.
4. Prefers the smallest/simplest repeating Hopper Pattern (Section 18.1).
5. Minimizes absolute Ni deviation.
6. Avoids unnecessary pile switching / operational complexity.
7. Deterministic Pile ID tie-break.

> Example: if `17 : 31` estimates `1.1201%` and `1 : 2` estimates `1.118%`, and `1.118%` is inside the approved tolerance, `1 : 2` is preferred — matching Section 16's Candidate A/B illustration.

**Tie-breaking must be deterministic** — the same inputs always return the same ranked recommendation, using exactly the ordered dimensions in the ranking list above, terminating in deterministic Pile ID ordering (e.g. lexicographic) — never random. Do not introduce hidden numeric weights beyond what the ranking list states; any concrete scoring formula is an implementation-time decision, made only after Section 13.1 and Section 16's tolerance decision both close, and must ship with the tests in Section 37.

### 18.1 Default Recommendation Objective: Smallest Practical Repeating Hopper Pattern

For V2.4 core, the default Recommendation objective is:

> **Find the smallest practical repeating Hopper Pattern that achieves Target Ni or falls inside the approved tolerance.**

Small integer ratios such as `1:1`, `1:2`, `2:3`, or `2:1` are operationally preferable to unnecessarily large patterns such as `17:31` whenever both are acceptable against Target Ni/tolerance (Section 16). This is a **resolved** part of the core design — the user is **not** required to input a Target Total DT or a Target Total Tonnage for the initial V2.4 core Recommendation; those remain **optional future constraints** (Section 41, Decision 7), not a core requirement.

**This does not resolve Section 13.1.** "Smallest practical repeating pattern" describes the *shape* of the desired output (a small integer ratio); it says nothing about what upper bound, if any, constrains how many times that pattern can repeat, or what a pile's entered Jumlah Unit legitimately allows — that is still the separate, blocking question in Section 13.1.

## Section 19 — Higher Grade Grouping, Unit Ratio, Tonnage Ratio

**Higher Grade grouping**, for hopper-pattern purposes only:

```
Higher Grade = HGLO + MGLO
Lower Grade  = LGLO
```

Primary operational ratio: `HGLO/MGLO : LGLO`.

> Example: HGLO = 2 DT, MGLO = 7 DT, LGLO = 18 DT → Higher Grade = 9 DT → primary unit ratio `9 : 18` → simplified `1 : 2`.

**Unit Ratio** is the GCD-simplified integer ratio of DT counts:

| Raw ratio | Simplified |
| --- | --- |
| 6 : 12 | 1 : 2 |
| 8 : 12 | 2 : 3 |
| 10 : 15 | 2 : 3 |
| 7 : 11 | 7 : 11 (already coprime) |

Meaning: `1 : 2` means, operationally, **1 DT of HGLO/MGLO for every 2 DT of LGLO**. This is the primary field-facing ratio (Section 20).

**Tonnage Ratio** is always calculated separately from the unit ratio — the two must never be conflated when tonnes/DT differ.

### Worked Example B — Unit Ratio vs Tonnage Ratio

```
Higher Grade: 1 DT × 50 t/DT = 50 t
LGLO:         2 DT × 45 t/DT = 90 t

Unit ratio:    1 : 2
Tonnage ratio: 50 / (50+90) : 90 / (50+90)  =  35.7% : 64.3%
```

Displaying `1:2` DT as if it were `33.3%:66.7%` tonnes would be incorrect here — the tonnage ratio must be computed and shown independently whenever tonnes/DT differ across the compared groups.

**Hard rule — tonnage still controls the math, regardless of how the Hopper Pattern is displayed.** Even though the Hopper Pattern is shown as a DT/load ratio (Section 20), Estimated Ni MUST be computed from Section 14's tonnage-weighted formula using each group's actual tonnes, never from the unit ratio directly. For the example above, Estimated Ni uses `50 t` and `90 t` — it must never be computed as `(1×NiHigher + 2×NiLGLO) / 3`, i.e. a simple average weighted by unit counts, unless tonnes/load are genuinely identical across every group being combined.

## Section 20 — Hopper Pattern and Hopper Sequence

**Hopper Pattern is the single most visually prominent Recommendation result on mobile.** Estimated Ni is important verification information, but it sits *below* the operational instruction, never above it.

```
┌──────────────────────────────┐
│       HOPPER PATTERN         │
│                               │
│           1 : 2               │
│                               │
│  HGLO/MGLO         LGLO       │
│     1 DT            2 DT      │
│                               │
│           REPEAT              │
└──────────────────────────────┘
```

**Hopper Sequence** — when multiple piles contribute to Higher Grade or LGLO, show an actionable per-pile batching order:

```
HOPPER SEQUENCE

1. Pile A     1 DT
2. Pile B     1 DT
3. Pile C     3 DT
↻ REPEAT
```

This sequence is an **operational batching instruction only**. The engine must not claim an exact truck-by-truck interleaving carries scientific mixing significance unless such a rule is separately defined and approved — it documents *what to load next*, not a mixing-physics guarantee.

### 20.1 Hopper Pattern Is a Feed Ratio, Not a Fleet Inventory Statement

The Hopper Pattern `1 : 2` is an **operational feed instruction**: for every 1 higher-grade DT/load entering the hopper, use 2 LGLO DT/loads. It must **not** be silently interpreted as any of the following:

- That only three physical trucks exist.
- That exactly one physical Higher-Grade truck and exactly two physical LGLO trucks are dedicated to this pattern.
- That those trucks are consumed or retired after one cycle.

The same physical trucks may participate repeatedly — the Hopper Pattern describes a **load-arrival / feeding pattern to repeat**, not a one-time physical fleet allocation, unless a future, explicitly approved fleet-allocation model states otherwise. Implementation and UI copy must never equate the hopper load ratio with a physical fleet allocation ratio — this distinction is the direct consequence of Section 13.1 still being unresolved: until Jumlah Unit's meaning is confirmed, the Hopper Pattern's DT/load counts cannot be assumed to map one-to-one onto a fixed truck count at all.

## Section 21 — Maximum Complete Cycles (Future / Conditional — NOT V2.4 Core)

**This is no longer a V2.4 core requirement.** An earlier draft calculated "maximum complete cycles" directly from a pile's entered Jumlah Unit, treated as consumable DT inventory:

```
Maximum complete cycles = min( floor(HigherGradeAvailable / HigherGradeUnitsPerCycle),
                                floor(LGLOAvailable        / LGLOUnitsPerCycle) )
```

That calculation assumes DT availability is a depletable material quantity. Per Section 13.1, that assumption is **not proven** — if Jumlah Unit means physically reusable trucks (Interpretation A), this formula does not represent how many hopper cycles are operationally possible at all, since the same trucks can keep returning indefinitely within a shift. Computing "cycle exhaustion" from a raw physical truck count would be actively misleading in that case.

**Therefore:** Maximum Complete Cycles is moved out of approved V2.4 core and is a **future, conditional feature**. It may only be calculated once the application has a clearly-defined, genuinely finite quantity to divide against, such as:

- A planned rit/load count (Interpretation B of Section 13.1, if confirmed).
- A planned tonnage target for a defined window.
- A defined finite available-material tonnage (e.g. a stockpile survey figure, not a truck count).
- An explicitly defined recommendation window (e.g. "next 4 hours").

Do **not** calculate cycle exhaustion from physical truck count alone. The worked arithmetic above (`min(floor(...), floor(...))`) remains *mathematically* valid once a genuine finite quantity is defined — it is the *interpretation* of Jumlah Unit as that finite quantity which is unresolved, not the arithmetic itself. Re-approval of this section as V2.4(.x) core requires Section 13.1 to close in favor of Interpretation B, or a separate finite-quantity input to be added to the UI.

## Section 23 — Dome/Pile Action Recommendation (USE / LIMIT / STOP)

Action vocabulary: **USE**, **LIMIT**, **STOP** — dynamic, per-target recommendations, never permanent classifications of a pile.

**Hard rule: a low-Ni LGLO pile is not automatically STOP.** Action depends jointly on:

- Target Ni
- The current candidate/blend condition (too high vs. too low vs. within target)
- Pile Ni
- Tonnes/DT
- Available alternatives
- Effect on the achievable recommendation

> Example: Target = 1.12%. If the current/recommended blend condition is *too high*, an LGLO pile is useful (USE) to pull the blend down. The **same LGLO pile** may warrant LIMIT/STOP once the blend is already at or below target — because now more LGLO would push it further away, not closer.

**Never define a universal rule such as "Ni below X → STOP."** Action must always be evaluated against the current target and blend state, never against a static Ni threshold alone.

### 23.1 Deterministic Action Semantics

USE/LIMIT/STOP was previously described only conceptually; the following semantics are the deterministic basis implementation must use, refined from the Owner's operational review.

**USE** — a pile/dome is USE when:

1. it has a positive allocation in the primary recommended Hopper Pattern (Section 23.2); **and**
2. its inclusion contributes to the selected operational solution.

USE does not mean the pile is permanently preferred — only that the *current* primary recommendation includes it.

**LIMIT** — a pile/dome is LIMIT when:

1. it may still be used operationally; **but**
2. additional usage beyond the recommended allocation/pattern worsens the blend's distance from Target Ni, or risks moving it outside the approved tolerance.

LIMIT is contextual — it does not mean the pile itself is intrinsically bad, only that *more of it than currently recommended* is counterproductive right now.

**STOP** — the strongest status, used conservatively. A pile/dome may be STOP for the **current recommendation only** when **all three** hold:

1. Its allocation in the primary recommendation is zero; **and**
2. Adding one additional DT/load of that material moves the resulting blend farther away from Target Ni (per the Pile Impact calculation below); **and**
3. No feasible, within-target/tolerance recommendation requires that pile.

STOP means: *"Do not feed this source in the next recommended pattern under the current conditions."* It does **not** mean: permanently stop the dome; permanently classify the material as unusable; or blacklist it from future calculations. A new sampling result (Section 17) or a changed Target Ni can immediately change STOP into LIMIT or USE — action status is recomputed from scratch every time, never carried forward as sticky state.

### 23.2 Action Status Depends on the Primary Recommendation — Not Computed Independently

Action status must be derived **after** a primary recommendation is selected, never computed in isolation before it:

```
Inputs
  ↓
Candidate generation (Section 18)
  ↓
Primary Recommended Hopper Pattern (Section 18.1)
  ↓
Pile/Dome actions
  ├── USE
  ├── LIMIT
  └── STOP
```

Computing USE/LIMIT/STOP independently of the primary recommendation would let the two disagree with each other (e.g. a pile marked STOP that the primary recommendation actually allocates DT to) — a circular/inconsistent state this architecture explicitly forbids. Section 23.1's definitions are only meaningful once "the primary recommended Hopper Pattern" already exists.

### 23.3 Action Behavior When Target Is Not Achievable

When Target Ni is not achievable (Section 24), avoid issuing misleading absolute STOP decisions solely because no within-tolerance candidate exists — the definitions in Section 23.1 assume a within-target-or-tolerance primary recommendation exists, which is not true in this case. Instead, actions must be evaluated relative to the **best attainable candidate** (Section 24): a pile is USE if the best-attainable candidate allocates it, LIMIT if more of it worsens progress toward Target Ni from that best-attainable point, and STOP only if it is unallocated in the best-attainable candidate *and* adding it would move further from Target Ni than the best-attainable result already is. The best-attainable candidate, not an unreachable target, is always the action baseline.

### Pile Impact (marginal contribution)

For explanation/detail, the engine may compute the marginal effect of adding one DT of a pile to the relevant blend state — `CurrentNi`/`CurrentTonnage` here mean the same current **planned** blend baseline defined in Section 25.1, never a cumulative actual production figure:

```
New Ni = (CurrentNi × CurrentTonnage + PileNi × TonnesPerDT)
         ─────────────────────────────────────────────────────
                    CurrentTonnage + TonnesPerDT

Impact = New Ni − Current Ni
```

```
Example display:
  L37_13   Ni 0.85%   Impact / DT: -0.012%
```

Impact ranks sources by *direction and magnitude* of effect — but the action status (USE/LIMIT/STOP) must never be derived from impact sign alone; direction relative to the target still governs (a negative impact is desirable when the blend is too high, undesirable when it is already too low).

```
with current available material

Best attainable Ni:  1.087%
Target:               1.120%
Gap:                 -0.033%
```

The best attainable blend is still shown, but labeled explicitly as the best attainable result, not as a successful recommendation. Dome Actions (USE/LIMIT/STOP) in this state follow Section 23.3, not Section 23.1's within-target definitions — they are evaluated relative to the best attainable candidate, never issued as if the unreachable target had been met.

## Section 25 — Planned Blend Recovery (New Dome / Recovery Requirement)

When available material cannot reach Target Ni, calculate the **minimum Ni** an additional/new source must have to correct the blend, for an arbitrary added tonnage.

### 25.1 V2.4 Core Baseline — Explicit and Non-Ambiguous

`CurrentNi` and `CurrentTonnage` in the formula below are ambiguous unless the baseline is pinned down. **For V2.4 core, Recovery Requirement is calculated against the CURRENT PLANNED BLEND STATE already entered inside Calculate — nothing else:**

- It is **not** cumulative actual FPP production.
- It is **not** automatically taken from Monitor.
- It is **not** automatically taken from Report.
- It is **not** a lab-feed cumulative result.

Conceptually:

```
Current planned blend (Calculate's own piles/inputs)
        +
proposed additional/new dome
        ↓
   Target Ni
```

`CurrentNi`/`CurrentTonnage` are the weighted Ni and total tonnage (Section 14) of whatever blend is currently defined inside Calculate — e.g. the best blend achievable from the currently entered piles, or the primary Recommendation's candidate. If a Recovery calculation is requested and no clearly-defined finite baseline blend exists yet inside Calculate (e.g. no piles entered, or Recommendation has not been run), the UI must ask the user for or derive an explicit, clearly-defined finite baseline rather than inventing one silently.

**Terminology requirement:** label this feature "**Planned Blend Recovery**" in UI copy and documentation, never "Actual Shift Recovery" or similar wording that implies correcting the whole shift or whole FPP production — V2.4 core does not know real cumulative feed Ni, authoritative tonnage already fed, or remaining planned production tonnage (Section 28), so it must never display a correction as if it were correcting actual cumulative production.

```
AddedTonnage = AddedDT × TonnesPerDT

RequiredNewNi = TargetNi × (CurrentTonnage + AddedTonnage) − CurrentNi × CurrentTonnage
                ───────────────────────────────────────────────────────────────────────
                                        AddedTonnage
```

### Worked Example E — Planned Blend Recovery Requirement

```
Current planned blend (inside Calculate):  1.085%,  1000 t
Target:                                     1.120%
Candidate correction: 5 DT × 50 t/DT = 250 t

RequiredNewNi = (1.120 × 1250) − (1.085 × 1000)
                ───────────────────────────────
                             250

              = (1400 − 1085) / 250
              = 315 / 250
              = 1.260%
```

```
PLANNED BLEND RECOVERY — NEED NEW DOME
For 5 DT × 50 t/DT
Minimum Ni ≥ 1.260%
```

**Recovery Options** — because the required Ni depends on how much new tonnage is added, the UI should be able to show several scenarios:

```
NEW DOME REQUIREMENT

 5 DT   ≥ 1.55%
10 DT   ≥ 1.35%
15 DT   ≥ 1.28%
```

The specific DT presets shown (5/10/15 above) are illustrative only — **do not hardcode these as business constants in the architecture.** They are UI presets to be finalized during implementation (Section 41, Decision 3). The underlying `calculateRequiredNewDomeNi(...)` function must accept arbitrary Added DT and Tonnes/DT — never a fixed preset list baked into the calculation itself.

## Section 27 — Sampling-Driven Field Workflow

This workflow is central to V2.4 and should directly inform the UI's step order.

**Start of shift:**

1. User sets Target Ni.
2. User enters active Pile IDs.
3. User enters latest sampled Ni per pile.
4. User enters Jumlah Unit per pile (its exact operational meaning — physical fleet vs. planned loads — pending Section 13.1).
5. User enters tonnes/DT per pile.
6. Calculate Recommendation.
7. Field team follows the Hopper Pattern.

9. Recalculate (Section 17).
10. Review the (possibly changed) Hopper Pattern.
11. Review updated USE/LIMIT/STOP Dome Actions.
12. Continue operation.

**If target becomes impossible:**

13. Show TARGET NOT ACHIEVABLE (Section 24).
14. Show the Planned Blend Recovery minimum-Ni requirement (Section 25).

## Section 31 — Performance, Search Space, and Determinism

Naïve Cartesian enumeration over per-pile integer ranges can explode combinatorially as the number of piles or the size of whatever operational bound Section 13.1 eventually confirms grows. Implementation must benchmark search complexity before choosing a concrete optimizer; acceptable deterministic strategies include bounded enumeration, dynamic programming, branch-and-bound, grouped class search followed by per-pile allocation, and pruning candidates outside useful target bounds. Since Section 18.1's default objective is the smallest practical repeating pattern (typically small integer ratios), the search can often be framed as "enumerate small ratios first, verify feasibility and tolerance" rather than exhaustively enumerating every possible per-pile allocation. **No AI/heuristic optimization of any kind.**

Correctness tests (Section 37) must be written independently of the eventual algorithm choice, so the algorithm can be swapped later without invalidating the test suite — the tests assert on *results* (feasibility, tolerance compliance, determinism, ranking behavior), not on *how* a particular candidate was found.

Determinism is non-negotiable: identical inputs must always produce identical output, including identical tie-breaks (Section 18) and identical alternative ordering (Section 22). No random ordering anywhere in the engine.

## Section 37 — Testing Architecture

Exhaustive tests must exist before/alongside implementation, mirroring the existing `tests/*.test.mjs` convention (e.g. `tests/license-service.test.mjs`, `tests/contractor-directory-core.test.mjs`).

**Weighted calculation:**
1. One pile.
2. Two equal-tonnage piles.
3. Piles with different tonnes/DT.
4. Multiple (3+) piles.
5. Zero total tonnage is rejected (Section 29), not silently defaulted.
6. No premature rounding — verify via a case where rounding-before-summing would produce a different (wrong) answer than rounding after.

**Classification (reused, not reimplemented):**
- Boundary tests around the current thresholds (Section 11's table), run against whatever the authoritative function is at implementation time — this test suite must fail loudly if Calculate's classification ever diverges from Monitor/Report's.

**Ratio:**
1. `6:12 → 1:2`
2. `8:12 → 2:3`
3. `7:11` remains `7:11`
4. Explicit zero-side cases (e.g. `0:12`, `12:0`) defined and tested.

The four groups above (Weighted calculation, Classification, Ratio) exercise only Blend-mode-safe math and can be written before Gate A (Section 40) closes. The two groups below (Recommendation, Recovery) exercise the search/ranking engine and **must not be finalized until Gate A closes** — they are listed here to define the target coverage, not as tests safe to write against an unresolved search boundary today.

**Recommendation** (post–Gate A):
1. Exact target achievable.
2. Target achievable only within tolerance.
3. Multiple solutions exist → simpler operational ratio is preferred (Section 16's Candidate A/B scenario).
4. Piles with different tonnes/DT.
5. The confirmed operational constraint from Section 13.1 is never exceeded (exact assertion depends on which interpretation the Owner confirms).
6. Integer DT/load only — no fractional candidate ever produced.
7. Deterministic ranking — same input, same output, run twice.
8. No feasible target — TARGET NOT ACHIEVABLE path exercised, with actions evaluated per Section 23.3.
9. Highest Ni alone is not automatically selected (Section 26).
10. Changing a pile's sample Ni changes the result predictably (Section 17).

**Recovery** (post–Gate A, and dependent on Section 25.1's baseline):

1. Required new-dome Ni formula (Worked Example E, Section 25), computed strictly against the current planned blend baseline (Section 25.1) — never a value that implies cumulative actual production.
2. Different Added DT values.
3. Different tonnes/DT values.
4. Already-at-target case (required Ni should equal or be below current Ni, not misleadingly high).
5. Impossible/unrealistic required-Ni result (e.g. > 100% or absurdly high) is still displayed honestly, not clamped or hidden.
6. No division by zero (`AddedTonnage = 0` is a validation error, not a crash).

**Action recommendation** (post–Gate A, depends on a primary recommendation already existing per Section 23.2):
- USE/LIMIT/STOP changes with target direction (Section 23's LGLO example, both directions).
- LGLO is never universally STOP.
- The same pile receives different actions under different blend conditions in the same test run.
- STOP is only asserted when all three Section 23.1 conditions hold simultaneously — a test asserting STOP from zero-allocation alone (without also checking directional impact and absence of a feasible alternative) is insufficient.
- Under TARGET NOT ACHIEVABLE, actions are evaluated relative to the best-attainable candidate (Section 23.3), not relative to the unreachable target.
